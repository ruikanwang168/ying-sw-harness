# proto-generator

## 用途

`proto-generator` 是面向 AI 辅助产品原型生成的流程控制技能。

最终目标是根据需求文档生成完整、可运行或可预览的产品原型，避免遗漏页面、子页面、弹窗、抽屉、路由和深层交互。

本技能必须能够在有或没有 `prototype-starter` 的情况下工作。不得要求用户先初始化 starter 工作区。检测到 starter 工作区时，将其作为增强的生成环境；否则继续以独立模式执行。

本技能不要求 AI 一次生成所有原型页面，而是通过以下环节控制完整的生成过程：

- 输入诊断
- 功能目录提取
- 页面清单与页面关系规划
- 人工评审文档
- 可执行的原型索引
- 逐页生成
- 任务状态跟踪
- 生成文件记录
- 路由与交互验证
- 最终完整性检查

## 工作区检测

生成原型文件之前，检查目标目录。

只有当目标目录包含以下 starter 标志文件和目录时，才将其视为 `prototype-starter` 工作区：

```text
DESIGN.md 或 design.md
design-system/
shared/
scripts/new-feature.cjs
```

如果这些文件或目录不存在，继续以独立模式执行。不要停下来要求用户运行 `prototype-starter`。

### 独立模式

未检测到 starter 工作区时，使用独立模式。在此模式下：

1. 诊断需求输入。
2. 生成 `prototype-index-review.md`。
3. 生成经过确认的 `prototype-index.md`。
4. 逐页生成原型文件。
5. 维护 `prototype-generation-log.md`。
6. 执行完整性检查，产出 `prototype-completeness-check.md`。
7. 使用选定或推断的技术栈，确保结果可运行或可预览。

### Prototype-Starter 兼容模式

检测到 starter 工作区时，使用 starter 兼容模式。在此模式下，本技能继续负责页面覆盖和任务控制，starter 资源则负责产品设计还原度和项目结构。

附加规则：

1. 读取根目录的 `DESIGN.md` 或 `design.md`，作为产品设计约束。
2. 存在 `design-system/fidelity-guardrails.json` 时，读取该文件。
3. 存在 `design-system/shared-registry.json` 时，读取该文件。
4. 根据 `prototype-index.md` 中已确认且未受阻的任务生成 `feature-manifest.json`。
5. 优先使用 `node scripts/new-feature.cjs --manifest <feature-manifest.json>` 创建页面和场景骨架。
6. 生成的页面必须复用 starter 的共享 CSS/JS 资源。
7. 生成的页面必须保留 starter 元数据，例如 `data-page-key`、`data-page-kind`、`data-parent-page-key`、`data-surface`、`data-design-source-sha` 和 `data-design-contract-version`。
8. 存在相应脚本时，运行 `node scripts/check-prototype-compliance.cjs`。
9. 在最终完整性检查中，同时验证需求覆盖情况和 starter 兼容性。

starter 兼容模式不得创建已确认的 `prototype-index.md` 范围之外的页面、弹窗、抽屉、侧边面板、确认交互、路由或注册表条目。如果发现遗漏的界面，必须先将其加入索引并标记为 `Needs Confirmation`，再生成。

## 最终目标

本技能的最终产出是完整的产品原型。

评审文档、原型索引、任务表、生成日志和完整性检查都是过程控制产物，用于确保最终原型不遗漏必需的页面、子页面、弹窗、抽屉、状态、路由或核心交互。

根据用户的技术栈和项目背景，最终原型可以包含：

- React / Vue / HTML 页面文件
- 布局组件
- 路由配置
- 页面组件
- 弹窗和抽屉
- 模拟数据
- 导航交互
- 表格和表单交互
- 基础的空、加载中、成功和错误状态
- 可运行或可预览的原型项目

## 核心原则

不仅要控制输入，还要控制产出过程。

AI 必须：

1. 在规划之前诊断输入文档。
2. 提取或推断功能模块。
3. 提取或推断页面、子页面、弹窗、抽屉和交互。
4. 明确标记推断出的页面和不确定的交互。
5. 在编码之前生成人工评审文档。
6. 在人工评审之后生成可执行的 `prototype-index.md`。
7. 逐页生成原型。
8. 每个任务完成后，更新任务状态和生成文件记录。
9. 继续执行之前，回到索引核对。
10. 宣布原型完成之前，执行最终完整性检查。

## 适用场景

在以下情况下使用本技能：

- 用户提供了产品规格说明、PRD、功能需求、用户故事、需求调研记录、售前方案或其他需求文档。
- 用户希望 AI 编程代理生成产品原型。
- 原型包含多个模块、页面、子页面、弹窗、抽屉或复杂流程。
- 用户希望避免遗漏页面或隐藏交互。
- 不宜让 AI 一次性生成全部内容。
- 用户需要可控、可检查、逐页推进的原型生成过程。

## 执行模式

本技能支持以下执行模式：

| 模式 | 说明 |
|---|---|
| `interactive` | 默认模式。与用户确认关键检查点。 |
| `auto` | 假设风险较低时，自动生成索引和页面。 |
| `review-first` | 仅生成评审文档和索引，不生成原型页面。 |
| `strict` | 缺少关键信息时停止，不推断主要内容。 |
| `draft` | 生成基于假设的原型草稿，并明确标记不确定项。 |

默认模式：

```text
interactive
```

## 输入诊断规则

生成任何页面索引或原型代码之前，先诊断输入文档。

诊断应明确：

1. 用户提供的文档类型。
2. 输入是否包含足够的信息来规划原型生成。
3. 哪些信息是明确陈述的。
4. 哪些信息必须通过推断获得。
5. 哪些信息缺失并需要确认。
6. 技能应自动继续，还是暂停等待人工评审。

### 输入成熟度等级

| 等级 | 说明 | 默认处理方式 |
|---|---|---|
| L0 | 信息严重不足，只有一个想法或一句话描述。 | 列出补充信息的问题，可选生成基于假设的草稿。 |
| L1 | 有功能描述，但页面、流程和交互不明确。 | 生成包含较多待确认项的索引草稿。 |
| L2 | 有功能模块，以及部分页面或交互线索。 | 生成初步评审文档，并标记推断项。 |
| L3 | 页面、流程、交互和字段信息基本完整。 | 生成评审文档和可执行索引。 |
| L4 | 需求、设计规范、技术栈和项目结构均已具备。 | 生成可直接执行的索引和原型任务。 |

## 提取与推断规则

### 规则 1：优先提取明确提及的页面

如果文档明确提及某个页面，直接将其纳入。

示例：

- “项目列表页” → 纳入项目列表页
- “客户详情页” → 纳入客户详情页
- “成员管理弹窗” → 纳入成员管理弹窗

### 规则 2：根据操作推断页面

如果文档提及某项操作，推断其可能对应的页面或交互。

| 操作线索 | 可能对应的页面 / 交互 |
|---|---|
| 查询 / 搜索 / 浏览 | 列表页 |
| 添加 / 创建 / 新建 | 新建页或新建弹窗 |
| 编辑 / 修改 | 编辑页或编辑弹窗 |
| 查看 / 详情 | 详情页 |
| 删除 / 移除 | 删除确认弹窗 |
| 导入 | 导入弹窗或导入页 |
| 导出 | 导出操作，以及导出确认 / 结果 |
| 审批 / 驳回 | 审批弹窗或审批详情页 |
| 配置 / 设置 | 配置页 |
| 分配 / 分发 | 分配弹窗或抽屉 |
| 绑定 / 链接 / 关联 | 关联弹窗或选择页 |
| 上传 | 上传弹窗或上传区域 |
| 预览 | 预览页或预览弹窗 |
| 分析 / 检测 / 检查 | 结果页或任务详情页 |
| 发布 / 提交 | 提交确认和结果反馈 |
| 启用 / 停用 | 状态变更确认 |
| 复制 / 克隆 | 复制确认，或基于现有内容创建的页面 |

### 规则 3：推断子页面和深层交互

对每个列表页，检查是否需要：

- 搜索区域
- 筛选区域
- 表格
- 行操作
- 批量操作
- 详情页
- 新建页
- 编辑页
- 删除确认弹窗
- 导入 / 导出操作
- 空状态
- 加载状态
- 错误状态

对每个表单页，检查是否需要：

- 表单字段
- 校验规则
- 提交操作
- 保存草稿操作
- 取消操作
- 返回导航
- 成功反馈
- 错误反馈

对每个详情页，检查是否需要：

- 基本信息卡片
- 标签页
- 关联记录
- 时间线 / 操作日志
- 编辑入口
- 删除入口
- 返回导航

对每个弹窗或抽屉，检查是否需要：

- 触发操作
- 标题
- 主要内容
- 确认操作
- 取消操作
- 校验
- 成功反馈
- 错误反馈

### 规则 4：明确标记假设

绝不能将推断出的页面视为已确认的需求。

使用以下来源值：

| 来源 | 含义 |
|---|---|
| `Explicit` | 输入文档明确陈述了该页面或交互。 |
| `Inferred from operation` | 根据文档描述的操作推断出该页面或交互。 |
| `Inferred from product pattern` | 根据常见产品设计模式推断出该页面或交互。 |
| `Needs Confirmation` | 可能需要该页面或交互，但输入文档未提供足够依据。 |
| `Needs Input` | 缺少更多信息时，无法可靠规划该页面或交互。 |

## 人工参与规则

输入不完整或涉及重要假设时，本技能不应盲目继续执行。

以下情况下，必须暂停并请求人工评审：

1. 输入成熟度为 L0、L1 或 L2。
2. 生成的原型索引包含较多推断页面。
3. 生成的原型索引包含标记为 `Needs Confirmation` 的页面。
4. 生成范围不明确。
5. 页面关系存在歧义。
6. 核心交互缺失或依赖推断。
7. 最终完整性检查发现页面或交互缺失。

以下情况下，可以自动继续：

1. 输入成熟度为 L3 或 L4。
2. 页面任务定义清晰。
3. 当前任务没有未解决的假设。
4. 当前任务仅更新任务状态或执行常规检查。

默认规则：

> 由人确认方向和边界，由 AI 自动执行明确的任务。

## 评审文档规则

生成原型页面之前，必须先生成 `prototype-index-review.md` 文档，供人工评审。

评审文档应包含：

- 输入诊断结果
- 功能目录
- 页面清单
- 页面关系
- 推断页面
- 待确认项
- 缺失信息
- 用户修改区
- 确认结论

未经用户确认，不得将推断页面或不确定的交互视为已确认需求。

用户修改或确认评审文档后，应生成或更新 `prototype-index.md`，作为逐页生成原型的执行索引。

在 starter 兼容模式下，确认 `prototype-index.md` 后再生成 `feature-manifest.json`。除非用户明确选择草稿或基于假设的生成方式，否则不得将带有 `Needs Confirmation` 或 `Needs Input` 的任务纳入清单。

## 工作流程

### 步骤 1：诊断输入

读取输入文档并生成输入诊断结果。

此阶段不要生成原型代码。

### 步骤 2：提取功能目录

从输入文档中提取所有功能模块。

如果模块未被明确说明，则根据业务流程和操作推断。

### 步骤 3：生成页面清单

为每个功能模块识别：

- 主页面
- 列表页
- 新建页
- 编辑页
- 详情页
- 弹窗
- 抽屉
- 二级页面
- 配置页
- 结果页
- 空状态
- 错误状态

### 步骤 4：生成页面关系

识别：

- 入口页面
- 上一页面
- 触发操作
- 目标页面
- 返回路径
- 成功路径
- 失败路径
- 取消路径

在有助于表达关系时，生成 Mermaid 页面关系图。

### 步骤 5：生成人工评审文档

生成 `prototype-index-review.md`。

用户应能直接修改评审文档。

### 步骤 6：生成可执行的原型索引

经人工确认或修改后，生成 `prototype-index.md`。

该索引是逐页生成原型的权威依据。

在 starter 兼容模式下，还应根据已确认的任务生成 `feature-manifest.json`，使 starter 脚本能够创建项目骨架，同时不遗漏页面覆盖范围。

### 步骤 7：逐页生成原型

确认 `prototype-index.md` 后，逐页生成原型。

对索引中的每个任务：

1. 读取任务。
2. 将任务状态设为 `In Progress`。
3. 生成相应的页面、组件、路由、模拟数据或交互。
4. 确保生成的页面接入现有导航或路由。
5. 记录生成的文件。
6. 更新任务状态。
7. 对该任务执行局部一致性检查。
8. 只有当前任务完成或受阻后，才能继续下一个任务。

AI 不得默默跳过任务。

在 starter 兼容模式下，只要相应脚本可用，就应先通过 `node scripts/new-feature.cjs --manifest <feature-manifest.json>` 创建页面 / 场景骨架，再填充页面内容。

## 功能清单规则

`feature-manifest.json` 是需求规划向 starter 兼容项目生成交接的文件。只有在 `prototype-index.md` 已确认，或已根据用户评审完成更新后，才能生成该文件。

在 starter 兼容模式下：

1. 仅纳入已确认且未被 `Needs Confirmation` 或 `Needs Input` 阻塞的任务。
2. 保留 `iterationSlug`、`featureName`、`updatedAt`、`iterationName`、`sourceRequirement` 和 `sourceIndex`。
3. 将普通页面转换为 `pages[]` 条目，包含 `title`、`path`、`pageKey` 和 `surface: "page"`。
4. 将抽屉、模态弹窗、侧边面板、确认交互、导入向导及其他独立界面转换为其父页面下的 `scenarios[]`。
5. 为每个场景保留 `parentPageKey`。
6. 包含 `sourceTaskIds`，使完整性检查能够将清单条目追溯到索引任务。
7. 当任务对应根目录 `DESIGN.md` 中的模式或 `design-system/shared-registry.json` 中的条目时，包含 `designPatternRefs`。
8. 除非用户明确选择了 `draft` 模式，否则不得将不确定的任务或已推断但未确认的任务放入清单。

starter 兼容模式下的最小清单示例：

### 步骤 8：维护生成日志

每个页面生成任务结束后，更新 `prototype-generation-log.md`。

日志应包含：

- 任务 ID
- 页面名称
- 执行的操作
- 新建的文件
- 修改的文件
- 状态变更
- 发现的问题
- 下一个任务

### 步骤 9：执行最终完整性检查

对照检查以下内容：

- 输入需求文档
- `prototype-index-review.md`
- `prototype-index.md`
- `feature-manifest.json`（如有）
- 已生成的原型文件
- 路由与导航
- 组件使用情况
- starter 合规检查结果（在 starter 兼容模式下）

输出 `prototype-completeness-check.md`。

### 步骤 10：完成原型交付

只有满足以下条件后，才能认定原型已完成：

1. 所有已确认任务均已完成。
2. 没有遗漏必需的页面。
3. 没有遗漏必需的路由。
4. 没有遗漏必需的核心交互。
5. 完整性检查通过。
6. 项目能够按照选定的技术栈运行或预览。

## 原型索引字段

`prototype-index.md` 应包含以下字段：

| 字段 | 说明 |
|---|---|
| 任务 ID | 唯一任务标识，例如 T001 |
| 功能模块 | 业务功能模块 |
| 页面名称 | 待生成的页面或交互 |
| 页面类型 | 首页 / 列表页 / 新建页 / 编辑页 / 详情页 / 弹窗 / 抽屉 / 二级页面 / 结果页 |
| 迭代标识 | 迭代或功能文件夹的 slug，例如 2026-01-order-upgrade |
| 页面键 | 供需求 / 规格工具使用的稳定页面标识 |
| 界面类型 | page / drawer / modal / side-panel / confirm |
| 父页面键 | 场景界面所属的父页面 |
| 来源章节 | 任务来自输入文档的哪个章节 |
| 来源类型 | Explicit / Inferred from operation / Inferred from product pattern / Needs Confirmation |
| 上一页面 | 用户从哪里进入该页面 |
| 触发操作 | 打开该页面或交互的操作 |
| 下一页面 | 用户完成该页面后前往的位置 |
| 核心组件 | 表格、表单、筛选器、按钮、弹窗、标签页、卡片等 |
| 关键字段 | 已知的重要字段 |
| 是否需要路由 | 任务是否需要路由 |
| 建议文件路径 | 建议的实现文件路径 |
| 设计模式引用 | 相关的 DESIGN.md、starter 共享注册表或 UI 模式引用 |
| 是否写入清单 | 是否应将该任务写入 feature-manifest.json |
| 是否兼容 Starter | 该任务是否必须使用 starter 共享资源和元数据 |
| 状态 | Not Started / In Progress / Completed / Needs Confirmation / Needs Input / Needs Fix |
| 检查结果 | 缺失、不确定或已完成的检查结果 |
| 生成文件 | 该任务生成的文件 |
| 备注 | 补充说明 |

## 状态值

| 状态 | 含义 |
|---|---|
| `Not Started` | 任务尚未开始生成。 |
| `In Progress` | 任务正在生成中。 |
| `Completed` | 任务已生成并检查。 |
| `Needs Confirmation` | 任务在生成前需要人工确认。 |
| `Needs Input` | 任务缺少必要信息。 |
| `Needs Fix` | 任务已生成，但需要修复。 |
| `Skipped` | 有意不生成该任务。 |

## 原型生成规则

生成原型代码时：

1. 绝不能一次生成 20 个页面。
2. 每个任务仅生成一个页面或一个小模块。
3. 每次生成前，必须读取当前的 `prototype-index.md`。
4. 每次生成后，必须更新任务状态。
5. 必须记录生成或修改的文件。
6. 未经用户明确批准，不得创建索引中没有的页面。
7. 生成过程中发现遗漏页面时，将其添加为新任务，并标记为 `Needs Confirmation`。
8. 如果已生成的页面暴露出交互缺失，将其记入检查结果。
9. 如果页面依赖不确定的字段或规则，使用明确的占位内容，并在任务备注中标记。
10. 确保路由和导航与页面关系一致。
11. 多个页面共享模式时，优先使用可复用的布局和组件。
12. 尽可能在每个任务完成后保持原型可运行或可预览。

## 文件生成规则

对每个页面任务，判断是否需要生成或更新：

- 页面文件
- 路由配置
- 导航菜单
- 布局文件
- 共享组件
- 模拟数据文件
- 类型定义
- 弹窗 / 抽屉组件
- 样式文件
- README 或运行说明

不要生成不必要的文件。

## 任务完成标准

只有满足以下条件时，页面任务才能标记为 `Completed`：

1. 页面或交互已实现。
2. 需要入口路由或触发操作时，已为页面提供相应入口。
3. 必需的导航已接通。
4. 必需的组件已具备。
5. 已具备基本交互行为。
6. 已记录生成文件。
7. 不存在阻塞任务的 `Needs Input` 问题。

## 最终验收标准

只有满足以下条件时，才能认定原型已完成：

1. `prototype-index.md` 中的每个已确认任务都标记为 `Completed`，或明确决定 `Skipped`。
2. 每个已生成页面都有对应路由或入口。
3. 输入文档中明确陈述的每个页面都已出现在原型中。
4. 每个已确认的推断页面都已出现在原型中。
5. 每个列表页都具备预期操作。
6. 每个新建 / 编辑页都具备表单提交和取消行为。
7. 每个删除操作都有确认交互。
8. 每个详情页都有返回导航。
9. 不存在未解决的 `Needs Confirmation`、`Needs Input` 或 `Needs Fix` 任务。
10. `prototype-completeness-check.md` 确认没有遗漏必需的页面或核心交互。
11. 原型项目能够基于选定的技术栈运行或预览。

## 完整性检查规则

最终完整性检查必须验证：

1. 是否覆盖输入文档中的所有功能模块。
2. 是否生成输入文档中明确陈述的所有页面。
3. 推断页面是否经过确认，或已明确决定跳过。
4. 每个列表页是否具备预期的行操作和批量操作。
5. 每个新建 / 编辑表单是否具备提交、取消、校验和反馈行为。
6. 每个删除操作是否都有确认交互。
7. 每个详情页是否具备导航和相关操作。
8. 是否实现所有页面关系。
9. 已生成页面是否具备相应路由。
10. 生成文件是否与索引一致。
11. 原型中是否存在未在索引中登记的页面。
12. 是否仍有未解决的 `Needs Confirmation`、`Needs Input` 或 `Needs Fix` 任务。
13. 原型是否可运行或可预览。

## 默认响应行为

收到需求文档并调用本技能时，通常应从以下内容开始：

1. 输入诊断
2. 功能目录
3. 页面清单
4. 页面关系图
5. `prototype-index-review.md`

除非满足以下条件，否则不要直接开始编写原型代码：

1. 用户明确要求立即生成代码，并且
2. 页面索引已经确认，或者
3. 所选执行模式为 `auto` 或 `draft`。
