# 前端原型初始化与同步

本技能处理现有前端到高保真原型的全量复制和持续同步。原型沿用现有前端的页面、组件、样式、路由、表单和交互，后端接口改由浏览器本地模拟，工程目录固定为 `prototype-starter`。

## 先确定工作模式

以当前目录或用户指定目录为 `target`。先读取目标和正式源各自适用的 `AGENTS.md` 及必读文件。按项目忽略清单限制复制与检查范围。仓库要求结构检索使用图谱时，先检查索引覆盖，再用现有源码补足遗漏。

原型工程标志包括 `prototype-sync/` 下的同步清单或完整性索引，以及已知原型专用请求适配器和模拟引擎。目录判定如下。

1. 调用目录名为 `prototype-starter` 时，使用调用目录本身。其他情况检查 `target/prototype-starter/`。
2. 目标已是原型前端工程时，按用户本轮指定的范围增量同步。旧版原型可用 `package.json`、应用入口和模拟实现识别，也可由用户指定。
3. 调用目录为空时执行全量初始化。调用目录非空但预期的子目录不存在时，用户明确要求在这里创建原型工程即可新建该子目录。保留其他现有文件。
4. 遇到非空且无法识别为原型的同名目录时，核对工程归属，必要时请用户确认目标。已有文件和本地改动需要在同步前检查。

空目录判断忽略 `.gitkeep`、`.DS_Store`。优先使用用户指定的正式前端路径，其次检查当前目录和父级项目的工作区配置、包脚本、应用入口、路由、API 和共享包。排除原型自身及其他生成副本。多个不同产品的候选无法消歧时，列出路径并询问选择。找不到正式源码时，请用户提供其路径。

## 全量初始化

1. 读取正式前端的工作区和应用 `package.json`、脚本、锁文件、构建入口、路由注册、动态菜单、权限、API 类型、请求层、状态管理、页面、共享组件和静态资源。确认哪些包是构建和运行必需的。
2. 把完整前端工作区复制到 `prototype-starter/`，保留真实应用结构、页面、样式、共享包和构建所需配置。排除依赖、构建产物、缓存、日志、本地环境文件、凭据和后端工程。复制前确认目标不存在或为空，不覆写已有内容。
3. 在原型副本中设置独立包名、开发端口、存储命名空间和原型运行配置。除需隔离或模拟的基础设施外，保持正式页面、布局、路由、表单、字段、文案、组件、权限点和交互语义一致。正式前端保持只读。
4. 建立路由/菜单/页面/组件/API/权限/交互场景索引。每页记录正式源码位置、访问角色、入口、主要动作、表单规则、弹窗抽屉、关联数据、错误反馈和返回路径。对 API 记录调用页面、方法、路径、查询/请求类型、响应类型和模拟器处理状态。
5. 在统一请求边界或现有 API 适配层接入本地模拟，确保浏览器运行时不向后端发送业务请求。模拟列表、分页、搜索、筛选、排序、详情、创建、编辑、删除、启停、批量动作、关联关系、校验失败、权限失败和网络错误。写操作要更新浏览器持久化数据，刷新后回显，并有可发现的重置入口。
6. 为认证、租户、用户、菜单、角色权限、字典、文件上传下载、导入导出、验证码、扫码、WebSocket/SSE、iframe/监控页面等实际存在的特殊能力分别实现原型行为。未知接口或缺少适配器时显式失败并进入清单，不得伪造统一成功或空数据。
7. 安装依赖并复用项目的类型检查、测试、构建和浏览器验证入口。按验收矩阵逐条完成页面与交互验收。通过后用 `--full --write-baseline` 建立首份验收基线。命令和验收矩阵见 [references/diff-contract.md](references/diff-contract.md)。

初始化的最小交付物如下。

- `prototype-starter/` 可启动的原型工程
- `prototype-starter/README.md`
- `prototype-starter/prototype-sync/source-manifest.json`
- `prototype-starter/prototype-sync/api-manifest.json`
- `prototype-starter/prototype-sync/route-manifest.json`
- `prototype-starter/prototype-sync/prototype-index.md`
- `prototype-starter/prototype-sync/prototype-completeness-check.md`
- `prototype-starter/prototype-sync/generation-log.md`
- `prototype-starter/prototype-sync/accepted-baseline.json`（验收通过后创建或更新）

## 按范围增量同步

1. 以用户指定的需求、模块、页面、路由或操作为起点。用户要求同步但未给出范围时，先请用户指定；已有明确范围时直接开始。若用户只要求在当前原型上设计新需求，沿用已有原型，发现必须同步的正式前端依赖时再说明并确认所需范围。
2. 优先从已有索引、路由入口和相关源码定位文件。沿实际调用链纳入这个功能必需的菜单、权限、页面、局部组件、样式、API、模拟处理器和直接依赖。共享文件只读与本功能有关的片段，保留其他模块的代码和原型定制。超出已选功能及其必要依赖的同步项留待用户另选。
3. 用可重复的 `--scope` 传入双方相对于前端根目录的文件或目录，先看差异再做改动。细粒度需求优先选择具体文件，范围确实覆盖整个模块时再用目录。扫描只读取入选路径里的文件。两侧路径不同则都纳入，并记录对应关系。
4. 对照正式前端迁移所选功能，保持原型的请求适配器、本地模拟、存储结构和原型独有功能。涉及共享组件、菜单、鉴权或接口契约时，合并本轮必要的变更，并回归受影响的既有使用场景。
5. 验收后用 `--write-baseline`，再用可重复的 `--accept` 逐个写入已完整核对的文件。一个文件同时含其他需求的未同步改动时，把该文件留在待处理清单，保留旧哈希。没有全量基线的旧原型也可以局部验收，后续对未记录路径只比较现状。

更新 `prototype-sync/source-manifest.json`，记录需求、路径、纳入的依赖及原因、处理结果和遗留项。增量更新已有功能索引和验收记录中对应的条目。正式侧删除页面或 API 时，先核实动态注册、菜单和调用方。调用示例和基线规则见 [references/diff-contract.md](references/diff-contract.md)。

## 功能完整性验收

把页面覆盖和功能完成分开检查。逐模块对照正式页面、路由、菜单、权限和实际操作。检查每个页面的加载/空/错误状态、表单字段及必填/格式/跨字段校验、提交/取消反馈、行与批量操作、删除确认、详情返回、权限控制和关联数据。对每个 API 确认所有调用者、模拟处理器、参数/类型、成功/失败响应、持久化影响、刷新回显和无后端网络请求。

对列表、表单、详情、弹窗、抽屉和实时页面分别维护场景清单。场景清单至少包含访问角色、入口、触发操作、目标界面、成功路径、校验失败/服务失败路径、取消路径、下一步和返回路径。覆盖主子表联动、批量操作、文件能力、权限差异、刷新持久化和页面间跳转。新增场景在完成前标记为 `pending`，不要把已渲染页面直接标记为完成。普通按钮无动作、静默失败、永远成功、空白详情或静态假表格均视为功能缺失。

复用原型已有的 `prototype:check`、`test:prototype`、类型检查、构建、Playwright 或浏览器巡检入口。没有现成入口时，以本地浏览器操作或最小行为测试复现对应场景。全量模式逐模块验收，增量模式跑通每项新增和变更场景，并回归受共享组件、鉴权或请求层变化影响的既有场景。至少在业务后端未启动时运行原型，检查浏览器请求记录和未处理接口，实际操作写入并刷新确认回显。发现功能缺失后修复并复测。报告标记已运行通过、仅静态核对、待验收及实际阻塞。

使用以下结果文件。

- `prototype-sync/diff-report.json` 和 `prototype-sync/diff-report.md`
- `prototype-sync/prototype-index.md`
- `prototype-sync/generation-log.md`
- `prototype-sync/prototype-completeness-check.md`
- `prototype-sync/verification/` 下的测试、类型、构建和浏览器证据

只有满足以下条件才可以结束同步。

- 范围内新增或修改的页面、路由、API 和功能场景均有处理结果
- 没有未解释的 `missing`、`manual-review`、`pending` 或 `needs-input`
- 原型专用模拟层和数据持久化仍然可运行
- 已验收和待验收项均有记录。只有通过验收的文件可以进入基线
- 原型可启动或构建，且 README 已记录命令、账号、数据重置和模拟边界

## 推荐的源项目检查脚本

本技能附带的 `compare_frontend.mjs` 只负责可重复的文件、路由、API 和页面表面差异。它不替代业务语义判断。使用前阅读 [references/diff-contract.md](references/diff-contract.md)，了解输入、排除范围、报告字段和人工检查边界。

如果目标仓库已有 `prototype-starter`、`prototype-generator` 或其他原型流程技能，先保留其索引和设计契约，再将本技能的差异报告作为同步输入。参考流程中的页面清单、深层交互和完整性验收可以复用，但不能把 PRD 推断页面当作正式前端已实现的事实。
