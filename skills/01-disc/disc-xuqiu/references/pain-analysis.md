# 痛点与解决手段分析参考

这个文件只回答一件事：当需求已经基本说清后，怎么把“问题”拆成“痛点 -> 根因 -> 手段 -> 落地方式”。

## 适用时机

- 用户明确要分析方案。
- 用户想判断某个问题更适合用传统软件还是 AI。
- 需要补一份 `业务痛点与解决手段分析.md`。

## 分析顺序

1. 先写场景概述，用 2 到 4 句交代当前业务怎么运转、问题出在哪。
2. 找出 1 到 5 个核心痛点，不要把症状、细节和边角需求全塞进表里。
3. 每个痛点先写根因，再选手段，不要反过来先想技术名词。
4. 技术实现路径只写到“可落地方案”层级，不展开到接口、表结构、模型参数。
5. 如果某项信息不完整，直接标记“待确认”，不要编造现状和指标。

## 手段判断规则

### 优先用传统软件的情况

- 规则确定，判断条件稳定。
- 主要问题是录入、流转、统计、查询、校验。
- 结果需要一致、可审计、可追责。

常见手段：

- 流程自动化：审批流、状态流转、提醒、派单、闭环。
- 信息结构化：表单、台账、报表、搜索、筛选。
- 规则引擎：计算、校验、条件触发、权限判断。

### 可以考虑 AI 的情况

- 输入是大段文本、图片、语音等非结构化内容。
- 问题本质是理解、生成、识别、分类、归纳。
- 即使结果不是 100% 确定，也能接受人工复核或置信度机制。

常见手段：

- LLM：总结、问答、抽取、分类、生成。
- CV/AIGC：图片识别、质检、内容生成。
- ASR/TTS：语音转写、语音播报。

### 不要强行上 AI 的情况

- 规则已经固定，直接写死更简单。
- 目标是减少人为差异，而不是做模糊判断。
- 用户没有稳定样本、数据来源或复核机制。
- AI 只能让方案“看起来高级”，不能明显提升价值。

## 常见误判

| 错误写法 | 问题 | 更合适的写法 |
| :--- | :--- | :--- |
| 客服回复慢，所以接入 LLM | 先跳到技术，没写清根因 | 先判断是人手不足、知识分散还是流程卡顿 |
| Excel 很乱，所以做 AI 数据中台 | AI 与问题不匹配 | 先做结构化录入、统一数据源、报表统计 |
| 图片审核很慢，所以全量自动识别 | 忽略准确率和复核成本 | 一期先留档和抽检，二期再评估 CV |

## 推荐输出结构

```md
# 业务痛点与解决手段分析

## 1. 场景概述
- 当前业务如何运转
- 问题主要出在哪
- 本次分析聚焦什么范围

## 2. 深度分析矩阵

| 核心痛点 | 根因分析 | 解决手段 | 技术实现路径 | 预期价值 |
| :--- | :--- | :--- | :--- | :--- |
| 巡店记录分散 | 数据分布在微信群和 Excel 中 | 信息结构化 | 巡店任务 + 检查表单 + 查询报表 | 数据可查可统计 |
| 整改闭环弱 | 缺少责任人和状态流转 | 流程自动化 | 整改工单 + 超时提醒 + 状态机 | 闭环率提升 |
```

## 字段写法要求

- `核心痛点`：一句话写清真正的问题，不要写成功能名。
- `根因分析`：写为什么会发生，不要重复痛点表述。
- `解决手段`：写“流程自动化 / 信息结构化 / 规则引擎 / LLM / CV / ASR/TTS”这类手段，不要堆厂商名。
- `技术实现路径`：写到模块级或方案级，比如“表单 + 状态机 + 提醒机制”。
- `预期价值`：优先写可观察变化，如“统计时间下降”“闭环率提升”“错误率下降”。

## 输出约束

- 一次分析通常控制在 3 到 5 个痛点内。
- 没把握的数据不要写成确定数字。
- 没有必要时，不要同时给出传统软件和 AI 两套大方案。
- 如果当前版本只适合传统软件，直接说清楚，不需要硬补 AI 部分。
