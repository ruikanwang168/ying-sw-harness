# AI 开发说明书参考

这个文件只回答两件事：

- 如果文档要交给 AI 直接开发，最少还缺哪些实现信息。
- 如何把需求整理成 AI 更容易执行的实现说明书。

## 适用时机

- 用户明确说“这份文档要给 AI 开发”。
- 用户要的不只是 PRD，而是可直接用于编码、拆任务、生成模块的说明。
- 已经有 PRD，希望继续补一份实现规格说明。

## 生成前检查

在开始写 AI 开发说明书前，先确认下面内容是否基本明确：

- 本次版本范围是否已经收住。
- 技术栈是否已知；如果未知，要显式标记待定。
- 主要页面、模块或服务边界是否清楚。
- 关键角色和权限是否清楚。
- 关键数据对象和状态流转是否清楚。

如果这些前提还明显缺失，不要硬写完整实现说明书，先输出“开发前缺口清单”。

推荐结构：

```md
# 开发前缺口清单

- 缺少的前提
- 为什么会影响开发
- 当前可暂定的处理
- 需要用户确认的内容
```

## 这份文档和 PRD 的区别

| 文档 | 主要读者 | 重点 |
| :--- | :--- | :--- |
| `PRD.md` | 人类评审方 | 为什么做、做什么、范围和验收 |
| `AI开发说明书.md` | AI 开发执行方 | 怎么实现、哪些约束不能越界、做到什么颗粒度 |

不要把两份文档写成同一个东西换标题。

如果已经有 `PRD.md`，AI 开发说明书里的模块名、角色名、状态名、范围边界必须与 PRD 保持一致。

当用户已经明确要求开始生成文档时，默认直接创建或更新 `AI开发说明书.md`，把完整内容写入文件。
文件写入后，聊天里只保留简短结果说明，不复读整份正式文档。

## 推荐输出结构

```md
# AI 开发说明书

## 1. 开发目标
## 2. 本次交付范围
## 3. 技术栈与实现约束
## 4. 模块与页面清单
## 5. 数据模型
## 6. 接口契约
## 7. 权限矩阵
## 8. 状态流转与业务规则
## 9. 表单字段与校验
## 10. 异常处理
## 11. 测试点
## 12. 暂不实现项
## 13. 待确认事项
```

## 各模块写法

### 1. 开发目标

写清：

- 这次要交付什么。
- 交付边界在哪。
- 这份说明书默认服务于什么技术实现。

### 2. 本次交付范围

必须显式区分：

- 要实现
- 不实现
- 后续版本再做

这一步很重要，不然 AI 容易把相邻能力也一起做进去。

### 3. 技术栈与实现约束

至少写清：

- 前端技术栈
- 后端技术栈
- 数据库或存储方式
- 是否需要登录鉴权
- 是否有现成项目结构必须遵守
- 是否存在必须复用的仓库、目录、接口规范或 UI 规范

如果未知，不要编造；可以明确写成暂定方案。

### 3.1 改动边界

如果是增量模式，这部分要显式写清：

- 必须修改的模块
- 必须新增的能力
- 必须复用的现有能力
- 禁止改动的范围
- 当前待确认的改动点

不要写成“建议修改哪些地方”，能确定就写死，不能确定就放到待确认。

示例：

```md
## 改动边界

- 必须修改的模块：
  - 审批详情模块
  - 审批提交接口
- 必须新增的能力：
  - 抄送对象选择
  - 抄送记录持久化
  - 抄送通知触发
- 必须复用的现有能力：
  - 现有用户选择器
  - 现有审批流转记录展示组件
  - 现有消息通知发送机制
- 禁止改动的范围：
  - 审批模板引擎核心逻辑
  - 审批权限基础模型
- 当前待确认的改动点：
  - 抄送是否支持审批后补发
  - 抄送对象是否允许选择角色组
```

### 4. 模块与页面清单

推荐用列表或表格明确：

- 页面名 / 模块名
- 作用
- 访问角色
- 核心操作

### 5. 数据模型

至少列出：

- 实体名称
- 核心字段
- 字段类型或含义
- 关键关联关系

不要只写“有任务表、用户表”，要写到能支撑建模。

### 6. 接口契约

如果用户要求直接指导开发，这部分尽量写清：

- 接口名称
- 请求方式
- 路径
- 关键入参
- 关键出参
- 调用角色

如果当前还不够确定，至少先定义接口清单，不要完全跳过。

如果系统基于已有项目二次开发，优先写：

- 必须新增的接口
- 必须复用的接口
- 必须修改的接口

### 7. 权限矩阵

至少交代：

- 哪些角色可访问哪些页面
- 哪些角色可执行哪些操作
- 是否存在仅本人可见、仅总部可见、按组织范围可见等限制

### 8. 状态流转与业务规则

适合放：

- 任务状态变化
- 审批或整改流转
- 触发条件
- 不可逆规则

如果状态复杂，优先把枚举和转换条件写清。

### 9. 表单字段与校验

如果页面涉及输入，至少写：

- 字段名
- 是否必填
- 类型
- 校验规则
- 错误提示原则

这部分不写，AI 很容易补成“能跑但不符合业务”的表单。

### 10. 异常处理

至少考虑：

- 空数据
- 越权
- 重复提交
- 状态冲突
- 上传失败
- 依赖接口失败

不要只写“异常时提示错误”，要写清是什么异常、怎么处理。

### 11. 测试点

优先写：

- 核心流程是否打通
- 权限是否正确
- 状态流转是否正确
- 表单校验是否正确
- 边界值是否覆盖
- 与现有能力是否产生回归

### 12. 暂不实现项

必须显式写出来，避免 AI 自动加戏。

### 13. 待确认事项

把所有会影响开发决策但当前未确认的内容放这里，不要假定成立。

## 常见问题

| 问题 | 更合适的处理 |
| :--- | :--- |
| 只有 PRD，没有实现约束 | 补 AI 开发说明书 |
| 只有页面描述，没有数据模型 | 补实体、字段、关联 |
| 只有业务规则，没有接口边界 | 补接口清单或契约 |
| 把 AI 当成人类，默认它会自己补全缺失信息 | 显式写清约束和未确认项 |
| 没写暂不实现项 | 明确禁止范围蔓延 |

## 输出约束

- 这份文档服务于执行，不要写大段业务背景铺垫。
- 优先写结构、约束、接口、字段、状态，而不是空泛说明。
- 未确认的信息要标出来，不要用想当然的实现替代。
- 如果技术栈未知，可以给中性结构，但要明确这是暂定方案。
- 如果已有 `PRD.md`，不要重新发明一套模块划分或命名。
- 明确进入生成阶段后，优先落盘到 `AI开发说明书.md`，不要把整篇正式文档直接贴到聊天窗口。
