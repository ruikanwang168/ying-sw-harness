# 增量需求模式参考

这个文件只回答两件事：

- 在现有项目里做需求时，应该先锁定哪个模块、再学什么现状。
- 产出文档时，哪些内容必须和从零模式区分开。

边界说明：

- 这里只允许读取和分析现有项目内容，用于需求梳理和文档生成。
- 不允许修改任何代码、配置、脚本、数据库结构或项目文件。

## 适用时机

- 用户明确说“在现有项目上加功能”
- 用户说“这是二开”“在已有仓库里改”
- 用户提供了现有项目、开源框架、历史 PRD、已有模块说明

## 学习现状的优先顺序

不要直接把整个项目读一遍，按下面顺序收集：

1. 用户描述的增量需求
2. 用户指定的目标模块、页面、接口、目录或功能入口
3. 历史 PRD、旧需求文档、变更记录
4. 项目 README、架构文档、开发规范、代码规范
5. 与目标模块直接相关的代码
6. 基础框架文档或采用的开源项目文档
7. 与目标模块直接相连的上下游模块

如果用户没有明确指出模块，优先补问：

- 在哪个模块新增
- 哪个页面或入口新增
- 关联哪个接口、表、流程或目录

没有锁定模块前，不要展开大范围代码分析。

补问前先做一轮最小必要检索：

- 先从用户描述里提取模块名、页面名、按钮名、接口关键词、目录关键词
- 先看 README、目录结构、历史文档里是否已经出现这些关键词
- 再看与这些关键词直接相关的代码、接口和数据结构

如果已经能大致锁定目标模块，就不要再问用户“模块在哪”“目录在哪”这类仓库里本来能查到的问题。

## 现状学习时至少要弄清楚

- 当前系统是做什么的
- 当前技术栈是什么
- 目标模块是什么，代码大概在哪
- 已实现了哪些相关模块
- 本次需求最可能影响哪些模块
- 现有代码风格、目录结构、接口规范、命名规范
- 是否存在必须遵守的基础框架约束

如果这些都不清楚，不要直接写实现说明书。

能从代码和文档里确认的事实，优先自己整理出来，不要重复追问用户。
只把下面这类问题留给用户确认：

- 业务目标是否真的是这个方向
- 多个候选模块里到底改哪一个
- 新功能优先级和版本边界
- 旧行为是否要兼容
- 哪些规则允许调整，哪些规则必须继承

## 推荐先输出的现状摘要

```md
# 现状摘要

- 当前系统用途
- 目标模块
- 目标模块目录位置
- 当前技术栈
- 已实现相关模块
- 本次直接受影响模块
- 本次间接受影响模块
- 现有规范与约束
- 缺失信息与待确认项
```

示例：

```md
# 现状摘要

- 当前系统用途：面向企业内部审批流转的后台系统
- 目标模块：审批单详情模块
- 目标模块目录位置：`src/modules/approval/detail/`
- 当前技术栈：Vue 3 + TypeScript + Spring Boot
- 已实现相关模块：审批列表、审批详情、审批流转记录、审批模板管理
- 本次直接受影响模块：审批详情页、审批提交接口、审批记录表
- 本次间接受影响模块：消息通知模块、审批统计模块
- 现有规范与约束：前端沿用现有模块分层；后端接口遵循 `/api/approval/**` 命名；禁止改动审批模板引擎核心逻辑
- 缺失信息与待确认项：抄送功能是否要支持审批后补发；抄送对象是否允许选择角色组
```

## 目标模块代码分析

锁定目标模块后，优先细看这些内容：

- 当前模块职责
- 当前模块已有功能
- 关键文件和分层结构
- 关键接口
- 关键数据结构
- 状态流转或核心业务规则
- 现有命名和编码风格

这里要细，不要只看模块名字就开始写文档。

但范围也要收住，只看与本次需求直接有关的代码。

代码分析后，推荐先输出：

- 已经确认的现状
- 基于代码得出的初步判断
- 仍然模糊、必须由用户拍板的 1 到 5 个问题

示例：

```md
# 目标模块代码分析

## 模块
- 审批单详情模块

## 当前职责
- 展示审批单基础信息
- 展示审批流转记录
- 提交同意 / 拒绝操作

## 关键文件
- `src/modules/approval/detail/index.vue`
- `src/modules/approval/detail/components/FlowTimeline.vue`
- `src/api/approval.ts`
- `server/approval/controller/ApprovalController.java`
- `server/approval/service/ApprovalService.java`

## 当前已有能力
- 查询审批详情
- 提交审批动作
- 展示流转记录

## 关键接口
- `GET /api/approval/{id}`
- `POST /api/approval/{id}/action`

## 关键数据结构
- `ApprovalOrder`
- `ApprovalActionLog`

## 当前代码风格
- 前端按 `page + components + api` 分层
- 后端按 `controller / service / repository` 分层
- 接口返回统一使用项目已有响应包装结构
```

## 增量模式的人类版 PRD 要多写什么

除了常规 PRD 结构，额外补这几块：

- 现状说明
- 变更背景
- 目标模块
- 直接受影响模块
- 间接受影响模块
- 新增 / 修改 / 复用 清单
- 兼容性影响
- 回归风险

不要把增量需求写成“从零建设一个新系统”。

## 增量模式的 AI 开发说明书要多写什么

至少补这些信息：

- 当前技术栈
- 目标模块定位
- 现有目录结构或模块定位
- 本次需求涉及哪些模块层
- 直接受影响模块
- 间接受影响模块
- 新增接口 / 复用接口 / 改造接口
- 受影响数据结构
- 必须遵守的代码规范
- 回归测试点
- 禁止改动范围

## 新增 / 修改 / 复用 的判断

### 新增

- 当前系统完全没有这项能力
- 需要新增页面、接口、表或核心模块

### 修改

- 当前已有能力存在，但逻辑、流程、规则要调整
- 修改后可能影响现有用户路径

### 复用

- 当前已有能力基本够用，只需复用模块、接口、组件或数据结构
- 本次主要是组合、配置或轻量扩展

产出文档时，尽量把需求点按这三类标出来。

## 风险判断

增量模式下，优先关注：

- 是否破坏现有接口兼容性
- 是否影响现有权限逻辑
- 是否改变核心状态流转
- 是否影响历史数据
- 是否可能引入回归问题

## 常见问题

| 问题 | 更合适的处理 |
| :--- | :--- |
| 没先锁定目标模块就开始分析 | 先让用户指定模块、入口或目录 |
| 没看现状就直接出方案 | 先输出现状摘要 |
| 全仓库扫描，成本很高 | 只看相关模块和相关文档 |
| 增量需求写成全新系统 | 明确现状、改造点、影响范围 |
| 没区分新增 / 修改 / 复用 | 在文档里显式分类 |
| 没写回归风险 | 在 PRD 和 AI 说明书中都补上 |

## 输出约束

- 增量模式先写当前系统现状，再写变更需求。
- 增量模式先锁定目标模块，再细看该模块相关代码。
- 优先区分目标模块、直接受影响模块、间接受影响模块，而不是泛泛描述全部系统。
- 技术栈、规范、框架约束如果已知，要优先继承，不要擅自换方案。
- 不要因为信息不全就编造现有项目结构或编码规范。
- 不要把本来能通过代码检索确认的问题原样抛回给用户。
- 追问要少而准，只问代码里看不出来的业务决策问题。
- 只读取和分析，不修改项目中的任何内容。
