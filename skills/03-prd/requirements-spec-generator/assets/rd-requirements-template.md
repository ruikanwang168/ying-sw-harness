# 研发需求推荐模板

> **原则**：研发需求写的是**功能在系统中具体如何实现**；验收标准写的是**在具体操作与规则下，系统处理与结果是否符合规格**。  
> **核心回答**：这个功能在系统中具体如何实现。

---

## 研发需求：【功能名称 / 实现模块名称】

关联功能需求：【功能需求名称】

### 需求描述

【简要说明本研发需求要实现的系统能力、覆盖范围和预期结果。】

> **公式**：
> 当【用户角色】在【页面/模块/场景】执行【关键操作】时，
> 系统应根据【业务规则/数据规则/权限规则/状态规则/异步处理规则】完成【处理逻辑】，
> 并返回 / 展示 / 保存 / 更新【结果】。



### 数据与状态（可选）

> 描述功能涉及的业务对象、关键数据及状态流转，帮助研发理解数据变化。

| 业务对象 | 关键字段     | 读写规则   | 状态流转        | 外部交互 / 边界   |
| ---- | -------- | ------ | ----------- | ----------- |
| 订单   | order_id | 生成唯一ID | 待支付→已支付→已取消 | 支付系统API异步回调 |
| 用户   | user_id  | 唯一标识   | 活跃/冻结       | 身份验证模块      |

> **说明**：
>
> * 读写规则：字段写入、更新规则、唯一性约束
> * 状态流转：条件触发及允许跳转状态
> * 外部交互：仅列边界，协议细节另文档说明
> * 多分支、异常、异步或并发处理可在对应段落后用列表或表格补充说明。
> * **可选**：附流程图或状态机图辅助理解。

### 验收标准

> 说明如何验证功能是否实现，确保可测试、可验证。

> **公式**（AC1–AC5 均按此句式展开，验证具体处理与可观察结果）：
>
> 在【前置条件】下，  
> 当【用户 / 系统执行操作】时，  
> 系统应产生【可验证结果】，  
> 并满足【数据、状态、权限、异常、反馈】等要求。

#### AC1：【核心操作】处理正确

在【前置条件】下，  
当【用户 / 系统执行核心操作】时，  
系统应产生【可验证结果，如字段落库、状态变更、文件写入、页面展示内容】，  
并满足【数据、状态、权限、异常、反馈】等要求。

#### AC2：【查询/展示类操作】结果正确

在【前置条件】下，  
当【用户 / 系统执行查看、列表或详情操作】时，  
系统应产生【预期数据范围、字段与展示内容】，  
并满足【与需求描述一致、可追溯、权限可见】等要求。

#### AC3：规则与校验

在【触发规则的业务条件】下，  
当【用户 / 系统执行操作】时，  
系统应产生【允许或拒绝及分支处理的可验证结果】，  
并满足【数据、状态、权限、异常、反馈与规则定义一致】等要求。

#### AC4：异常与边界

在【异常或边界条件】下，  
当【用户 / 系统继续或重试操作】时，  
系统应产生【回滚、提示、保留中间状态等可验证结果】，  
并满足【不产生错误数据、重复数据或不可追踪状态】等要求。

#### AC5：集成与后续流转（如适用）

在【需要与外部模块/系统交接或触发后续流程】的前置条件下，  
当【用户 / 系统触发集成或流转操作】时，  
系统应产生【调用、回写、状态同步等可验证结果】，  
并满足【功能需求 AC5 中的后续流转要求及数据、状态、异常、反馈】等要求。

---

## 补充说明

- 每条功能需求可拆一条或多条研发需求（按模块、接口边界或核心操作拆）。
- **需求描述**是研发需求主体；撰写时可参考模板「公式」，**生成时勿输出**公式/说明类 blockquote。
- 研发需求可写用户原文中的产品名、模块名、接口名；仍避免无依据的表结构/算法细节（除非用户要求）。
- 若用户仅要「功能需求」而不要研发需求，不输出本模板结构。
