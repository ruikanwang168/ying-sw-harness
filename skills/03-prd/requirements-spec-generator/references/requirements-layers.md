# 三层需求体系

本 Skill 支持输出 **用户故事 → 功能需求 → 研发落地文档**，自上而下承接，勿混用句式。研发落地分两种**并列**形态：

| 形态 | 用途 |
|------|------|
| **常规研发需求** | 集成、状态流转、需求描述（简要说明 + 当…系统应根据…）+ 可选数据与状态 |
| **产品研发需求清单** | 页面/能力交付（字段、交互、五节验收） |

## 总览

| 层级 | 核心回答 | 典型表达 | 验收主语 |
|------|----------|----------|----------|
| **用户故事** | 谁在什么场景下，**为什么**需要这个能力 | 作为【用户】，在【场景】下，我希望【做什么】，以便【价值】 | **用户**应能够 |
| **功能需求** | 产品需要提供**什么功能**来满足用户故事 | 系统应**提供/支持**【功能能力】，帮助用户完成【业务任务】 | **系统应**支持/展示/按照（产品能力） |
| **常规研发需求** | 功能在系统中**具体如何处理** | 需求描述：简要说明系统能力、覆盖范围与预期结果；关键处理按「当…系统应根据…完成…并…」 | 在【前置条件】下，当…系统应**产生【可验证结果】并满足【数据、状态、权限、异常、反馈】** |
| **产品研发需求清单** | 研发要交付什么**页面/能力** | 作为【用户】…我希望通过【能力】…；用户点击/填写…系统应… | 五节验收（功能范围→验收结果） |

## 流转关系

```
用户故事（价值 / WHY）
    ↓ 满足故事所需的产品能力
功能需求（功能 / WHAT）
    ↓ 可交付的实现规格
研发落地（HOW）
    ├─ 常规研发需求（处理 / 集成 / 状态）
    └─ 产品研发需求清单（页面 / 交互 / 字段）
```

## 内容边界

| 不要放在 | 应放在 |
|----------|--------|
| 用户故事 | 菜单名、接口、集成步骤、字段级规则 | 功能需求 / 研发落地文档 |
| 功能需求 | SQL、API 路径、表结构、算法 | 常规研发需求 |
| 功能需求 | 逐字段页面布局、按钮级交互 | 产品研发需求清单 |
| 常规研发需求 | 「以便获得业务价值」、表单字段清单 | 用户故事 / 清单 |
| 产品研发需求清单 | 回调协议、跨系统状态机细节 | 常规研发需求 |

## 默认输出策略

Agent 在用户**未明确指定**输出哪些层时，按下列顺序决策。

### 1. 用户已明确指定 → 严格执行

| 用户说法 | 输出 |
|----------|------|
| 只要 / 仅 用户故事 | 仅用户故事 |
| 功能需求 / 产品需求 / PRD 功能 | 仅功能需求，或用户故事 + 功能需求（若同时提到故事） |
| 给后端 / 给研发 / 实现需求 / 集成 / 接口协作 / 状态同步 / 回写 | **常规研发需求**；若无功能需求基线则同时生成或先补功能需求 |
| 给前端 / 页面开发 / 产品研发需求清单 / 研发需求清单 / 页面需求清单 / 页面级需求 | **产品研发需求清单** |
| 笼统“给开发 / 给开发落地” | 按输入内容判定：页面字段交互为主用清单；系统处理与集成为主用常规研发需求；两者都有则分别输出；仍不明则短问 |
| 全套 / 三层 / 都要 / 全部需求 | 用户故事 + 功能需求 + 研发落地（按输入选常规研发需求和/或清单） |

### 2. 未指定且受众不明 → 短问优先

**触发**：未指定层级，且从输入无法判断是业务对齐、产品评审还是研发落地。

**话术（推荐）**：

> 需要输出哪几层？默认可提供 **用户故事 + 功能需求**；若需给研发落地，可加上 **常规研发需求** 或 **产品研发需求清单**。

用户不回复时，进入第 3 步兜底。

### 3. 未指定但输入可分类 → 按特征自动选层

| 输入特征 | 输出 | 理由 |
|----------|------|------|
| 主要为业务痛点、场景、价值；几乎无功能点与实现描述 | **仅用户故事**（可一句提示是否要功能需求） | 避免过早写「系统应提供」 |
| 描述能力、页面、流程；**无**跨系统分工、状态机、回写、跳转等 | **用户故事 + 功能需求** | **通例默认**；够 PRD 与评审 |
| 含**系统集成**、**双系统/多模块分工**、**状态同步**、**数据回写**、**外部工具衔接**、**接口协作**，或整体描述已像交付后端/集成 | **用户故事 + 功能需求 + 常规研发需求** | **升格**；集成类 |
| 含**页面、表单、列表、弹窗、抽屉**或用户要**按页面/清单**交付 | **用户故事 + 功能需求 + 产品研发需求清单** | 页面级交付 |
| 同时含页面交互与集成/状态/回写 | **用户故事 + 功能需求 + 产品研发需求清单 + 常规研发需求** | 前端页面规格与后端/集成处理分别落文档 |
| 明确在已有功能需求上补实现 | **常规研发需求**或**产品研发需求清单**（按用户要处理还是页面规格） | HOW 层补充 |

**识别「升格三层」的信号词（满足若干即可）**：

集成、对接、衔接、回写、同步状态、在 A 中配置后在 B 中执行、输入在 X 加工在 Y 输出在 X、接口、回调、模块、平台 + 开源组件/外部系统。

**识别「页面/清单交付」的信号词（满足若干即可）**：

给前端、页面级、清单、列表、表单、详情、弹窗、抽屉、字段、查询条件、表格字段、页面操作、行内操作、交互规则。

### 4. 兜底默认

仍无法分类且用户未回复短问时：

- 输出：**用户故事（按独立业务目标数量）+ 功能需求（按功能点多条）**
- **不默认**输出研发落地文档

**研发落地选型**：集成/回写/状态 → 常规研发需求；页面/表单/列表 → 产品研发需求清单；两者都需要 → 分别输出。

### 5. 生成顺序与关联

1. 先写用户故事（按独立业务目标数量；价值与 AC，用户应能够）
2. 再写功能需求（每条关联用户故事，系统应提供/支持）
3. 若含研发落地：常规研发需求关联功能需求，按模板写**需求描述**（简要说明 + 公式句式）+ 可选**数据与状态** + AC；产品研发需求清单按页面/能力拆条，验收用五节结构

禁止：只有研发落地却没有功能需求（除非用户仅给 FR 编号并要求只写 RD/清单）。禁止把两种研发落地结构混在同一章节。

## 策略速查表

```
用户明确层级？ ──是──→ 按用户要求
    │
    否
    │
受众是否不明？ ──是──→ 短问（默认 US+FR / 可选 +RD）→ 无回复则兜底 US+FR
    │
    否（可按输入分类）
    │
    ├─ 纯痛点/价值 ──────────→ 仅用户故事（+可选提示）
    ├─ 功能描述、无集成细节 ──→ 用户故事 + 功能需求  ★默认
    ├─ 集成/落地/多系统分工 ──→ 用户故事 + 功能需求 + 常规研发需求
    ├─ 页面/清单/表单列表 ────→ 用户故事 + 功能需求 + 产品研发需求清单
    └─ 补实现、已有 FR ───────→ 常规研发需求 或 清单（+关联 FR）
```
