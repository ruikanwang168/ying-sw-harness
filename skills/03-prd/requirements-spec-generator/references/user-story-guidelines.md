# 用户故事撰写指南

用户故事模式生成前**必须阅读**本文件、[requirements-layers.md](requirements-layers.md)，并严格遵循 [assets/user-story-template.md](../assets/user-story-template.md)。

若还需输出功能需求、研发需求，见对应指南；**手段与实现**不写进用户故事。

## 0. 两条原则

| 写什么 | 回答什么问题 |
|--------|----------------|
| **用户故事** | 用户想要什么**价值** |
| **验收标准** | 怎样判断这个价值**真的被满足** |

验收标准主语用 **「用户应能够」**，不用「系统应提供/展示/跳转」。

---

## 1. 核心诉求 vs 手段

| 类型 | 定义 | 非结构化数据示例 |
|------|------|------------------|
| **核心诉求** | 用户要完成的业务结果；去掉产品/工具名后仍成立 | 将非结构化业务文档加工成模型可用、可追溯的高质量数据集，并作为正式资产交付给微调/RAG/评测 |
| **手段** | 产品能力、集成、实现 | 写入**功能需求**与**研发需求**，不写入用户故事 |

**错误**：在「我希望」中写「新建任务、选文件集、进入某工具」。  
**正确**：在「我希望」中写业务目标；手段仅用于研发需求。

生成前：先写核心诉求（一句话）+ 手段清单；输出时以推荐模板为准。

### 页面密集输入的转换流程

当用户输入主要由页面结构、字段、按钮、弹窗/抽屉、跳转或外部工具组成时，按以下顺序处理：

1. 把原文中的页面、菜单、字段、按钮、跳转、iframe、工具名、系统名提取为**手段清单**。
2. 识别或推断这些手段服务的业务闭环：输入是什么、加工/处理目标是什么、交付给谁、后续用于什么。
3. 将用户故事写成**业务闭环**，而不是页面操作链路。
4. 将手段清单全部下放到功能需求或产品研发需求清单。

示例：

| 输入中的手段 | 用户故事中的抽象 |
|--------------|------------------|
| 新增二级菜单「数据集开发」 | 在统一治理入口内发起并管理数据集建设 |
| 搜索区、表格、任务名称点击详情 | 可定位并追溯一次数据集建设任务 |
| 新建任务抽屉、输入文件集、指定文件 | 按业务范围圈定输入材料 |
| 跳转 easy-dataset / iframe | 在不重复维护上下文的情况下完成加工配置与执行 |
| 输出高质量数据集 | 将结果作为正式数据资产交付后续模型流程 |

### 用户故事黑名单

用户故事正文和 AC 结论中默认不出现以下词或同类表达：顶部导航、左侧菜单、菜单、搜索区、表格、工具栏、按钮、图标按钮、抽屉、弹窗、字段、查询、重置、刷新、列配置、新建任务、编辑、删除、任务配置、点击、跳转、iframe、easy-dataset、系统应。

允许在功能需求、常规研发需求、产品研发需求清单中使用这些词。

## 2. 推荐模板（唯一正文格式）

### 用户故事

```markdown
## 用户故事

作为【用户角色】，
在【业务场景 / 触发条件】下，
我希望【完成某项任务 / 达成某个目标】，
以便【获得业务价值 / 解决用户问题】。
```

### 验收标准（至少三条）

| 条目 | 用途 |
|------|------|
| **AC1** | 主路径：用户执行关键动作后应获得的结果与质量标准 |
| **AC2** | 异常/边界：用户仍可以继续或获得修正路径，且不破坏核心任务 |
| **AC3** | 完成标准：结果可进入后续流程，相关人员可一致推进 |

每条 AC 固定四行：

```markdown
### AC1：【结果名称】

在【前置条件】下，
当【用户执行关键动作】时，
用户应能够【获得明确结果】，
并且【结果达到的质量标准 / 业务约束】。
```

## 3. 完整示例：非结构化数据治理

### 用户故事

作为**数据治理工程师**，  
在**非结构化数据治理**场景下，  
我希望**将非结构化业务文档加工成模型可用、可追溯的高质量数据集，并作为正式资产交付给微调、RAG 与效果评测使用**，  
以便**满足大模型项目的数据需求，且对业务与审计能说明材料范围与数据来源**。

### 验收标准

#### AC1：按业务范围完成加工与交付

在**非结构化治理项目已立项、业务文档已纳入统一数据环境**下，  
当**模型团队提出基于某批业务文档的数据集需求**时，  
用户应能够**按业务含义圈定加工范围并完成数据集交付**，  
并且**交付时能明确说明数据集对应的业务材料范围，而非笼统的整库导出**。

#### AC2：异常与边界下的可继续性

在**部分材料缺失、范围变更或加工未一次成功**等异常或边界条件下，  
当**用户需要调整范围或重新推进治理**时，  
用户应能够**获知问题边界并获得可执行的修正路径（如缩小范围、重跑某批）**，  
并且**不会因流程割裂而无法向需求方交代或交付错误范围的数据**。

#### AC3：结果进入后续模型流程

当**用户完成本轮非结构化数据集建设**后，  
用户应能够**将产出作为正式数据资产供微调、RAG 或评测流程直接使用**，  
并且**模型团队与治理方对「这批数据代表什么、来自哪次治理」可以达成一致并继续推进**。

## 4. 好/坏对比（节选）

| | 差 | 好 |
|---|----|----|
| 我希望 | 新建数据集开发任务并选择文件集 | 将业务文档加工成可追溯的高质量数据集并正式交付给微调/RAG/评测 |
| AC1 | 系统应提供文件多选器 | 用户应能够按业务含义圈定范围并完成交付 |
| AC2 | 系统应展示错误码 | 用户应能够获得修正路径且不影响核心交付 |

## 5. 数量与粒度

先判断用户输入包含几个**独立业务目标**，再决定输出几条用户故事。不要预设只能输出 1 条。

### 什么时候输出 1 条

- 输入只有一个用户角色、一个业务场景、一个端到端业务结果。
- 页面、按钮、字段、菜单、跳转很多，但它们服务同一个业务闭环。
- 多个操作只是同一目标的步骤，如新建任务、选择输入、进入加工、查看结果。

### 什么时候输出多条

- 调研记录、会议纪要、需求清单中出现多个互不依赖的业务目标。
- 不同用户角色、业务对象、业务阶段或管理目标需要分别验收。
- 去掉页面/系统名后，仍能得到多个不同的“我希望...以便...”业务价值。

### 拆分边界

- **一条故事 = 一个独立业务价值闭环**，每条仍用 `## 用户故事` + AC1-AC3 起。
- **不要按手段拆**：新建、查询、导出、跳转、字段展示、横向滚动条、按钮权限等通常不是独立用户故事。
- **可以按业务目标拆**：分类统计、数量汇总、按月分析、事项跟进、流程管理、资源沉淀、审批流转等若价值不同，应拆成多条。

### 出版工作部调研记录示例

当输入为出版工作部调研记录，内容包含以下独立需求时，宜输出 **9 条用户故事**：

1. 图书产品与音像产品分类统计。
2. 列表总数统计。
3. 选题按月查询。
4. 首页集中查看待处理/已办相关事项。
5. 出版工作流程管理与模块试用反馈。
6. 获奖情况总表与导出。
7. 作者/专家资源沉淀。
8. 重点项目申报时完整查看申报界面内容。
9. 合同审批中补充总经理签字等流程处理。

## 6. 输出前自检

- [ ] 「我希望」表达的是价值，不是手段/功能
- [ ] 用户故事条数来自独立业务目标数量，不是固定 1 条，也不是按页面控件拆分
- [ ] 含 AC1、AC2、AC3，且均为「用户应能够…并且…」
- [ ] 无「系统应提供/展示/跳转」
- [ ] 去掉产品名后故事仍成立（除非用户要求保留名称）
- [ ] 未输出研发需求结构（除非用户同时要求）
- [ ] 页面密集输入下，页面/字段/按钮/跳转已全部下放到功能需求或产品研发需求清单
- [ ] 若用户故事中出现黑名单词，已先重写为业务结果再输出
