# 产品研发需求清单撰写指南

阅读 [requirements-layers.md](requirements-layers.md)，并遵循 [assets/product-rd-requirements-list-template.md](../assets/product-rd-requirements-list-template.md)。

## 定位

| 维度 | 产品研发需求清单 | 常规研发需求 |
|------|------------------|--------------|
| 核心回答 | 研发要交付什么**页面/能力** | 功能在系统中**具体如何处理** |
| 典型场景 | 列表页、表单页、详情页、弹窗、配置页 | 集成衔接、状态回写、跨模块处理、回调 |
| 结构重心 | 功能范围 + 页面内容 + 交互 + 业务规则 + 验收结果 | 需求描述 + 可选数据与状态 + AC |
| 验收写法 | 分 5 小节，偏可测试的页面与交互结果 | AC 验证处理步骤与数据落点 |

**二者不互斥**：同一功能可同时输出清单（给前端/页面开发）与常规研发需求（给后端/集成开发）。

## 何时使用

**触发词**：产品研发需求清单、研发需求清单、页面需求清单、给前端的需求、页面开发、页面级需求、按页面拆研发需求、列表、表单、详情、弹窗、抽屉、字段、交互规则。

笼统“给开发”不直接等同于本模板：若输入主要描述页面、字段、按钮、表单、列表、弹窗、抽屉或交互，则使用本模板；若输入主要描述集成、状态、回写、接口协作或后端处理，则使用常规研发需求。

**推荐组合**：

| 用户要求 | 输出 |
|----------|------|
| 产品研发需求清单 | 仅清单（多条 `## 研发需求名称`） |
| 功能需求 + 产品研发需求清单 | 功能需求 + 清单 |
| 全套 + 产品研发需求清单 | 用户故事 + 功能需求 + 清单（是否加常规研发需求看是否有集成/处理细节） |
| 研发需求（未说清单，且偏处理/集成/后端） | **常规研发需求**，不用本模板 |
| 既要页面规格又要集成处理 | 清单 + 常规研发需求 |

## 命名规范

标题格式：**【模块/业务对象】-【页面/动作/能力】**

示例：

- `数据集开发任务-任务列表页`
- `数据集开发任务-新建任务弹窗`
- `退款管理-退款进度详情`

## 各节撰写要点

### 描述

- 使用「作为…在…我希望通过…以便…」四段式，与功能需求对齐但**落到具体页面/能力**。这是**页面能力描述**，不是用户故事。
- 「我希望通过【功能能力】」写**本页/本能力**能做什么，不写菜单路径或接口名。
- 不要把页面能力描述反向复制到用户故事。用户故事只写业务价值；页面、字段、按钮、跳转、iframe、外部工具留在本清单。

### 1. 功能范围

- 3–5 条 bullet，写本条目**必须交付的核心能力**。
- 与功能需求「功能范围」对齐，粒度更细、更贴近页面。

### 2. 页面内容

- **表单字段**：新建/编辑表单中的字段及必填/选填（可在字段后用括号注明）。
- **查询条件**：列表页筛选区字段。
- **表格字段**：列表列及关键展示规则（如状态标签）。
- **页面操作**：工具栏/页头按钮（新建、导出、批量删除等）。
- **行内操作**：表格每行的操作（查看、编辑、删除等）。
- 无对应 UI 时写「无」。

### 3. 交互规则

- 按**用户操作 → 系统响应**写，至少覆盖：入口打开、字段联动/校验、提交/保存反馈。
- 可写跳转目标、弹窗尺寸类型、刷新范围（整页/局部/关闭弹窗）。

### 4. 业务规则

- 数据校验、状态限制、权限可见性、条件分支。
- 与功能需求业务规则一致，补充**页面级**约束（如某状态下按钮禁用）。

### 5. 验收结果

- 至少 1 条**成功路径** + 1 条**异常路径**。
- 写可观察结果（数据展示、状态变更、提示文案），不写实现方式。

## 示例：退款进度查询-列表页

## 研发需求名称

退款管理-退款进度查询列表

## 描述

作为**客服**，  
在**处理用户退款咨询**场景下，  
我希望通过**退款进度查询列表**完成**快速定位订单退款阶段与异常原因**，  
以便**减少重复沟通并给出准确答复**。

关联功能需求：退款进度查询

## 验收标准

### 1. 功能范围

- 支持按订单号、用户手机号查询退款记录。
- 支持展示退款阶段、异常原因摘要与最近更新时间。
- 支持从列表进入退款详情。

### 2. 页面内容

- 查询条件：订单号、用户手机号、退款状态、申请时间范围。
- 表格字段：订单号、用户手机号、退款金额、当前阶段、异常原因摘要、最近更新时间。
- 页面操作：查询、重置。
- 行内操作：查看详情。
- 表单字段：无。

### 3. 交互规则

- 用户点击「查询」后，系统应按条件刷新列表并展示匹配记录条数。
- 用户清空必填查询条件并查询时，系统应提示至少输入订单号或手机号之一。
- 用户点击行内「查看详情」后，系统应打开退款详情抽屉并带入当前订单 ID。

### 4. 业务规则

- 仅**客服**与**客服主管**角色可访问本页。
- 当退款处于「处理中」且无异常时，异常原因摘要显示「—」。
- 当退款处于「异常」时，行内操作仅保留「查看详情」，不可发起人工干预（干预在详情页）。

### 5. 验收结果

- 在存在退款记录的前提下，当用户输入有效订单号并查询后，系统应展示对应记录且阶段与后台一致。
- 当用户输入不存在的订单号时，系统应展示空列表并提示「未找到匹配的退款记录」，且不报错。

## 自检

- [ ] 标题符合【模块/业务对象】-【页面/动作/能力】
- [ ] 描述为四段式，且聚焦本页/本能力
- [ ] 描述未被当作用户故事复用；用户故事中没有页面/字段/按钮/跳转等手段
- [ ] 验收标准含 5 个小节（不适用的项已标「无」）
- [ ] 未与常规研发需求混用「需求描述 + 数据与状态 + AC」结构
- [ ] 交互规则覆盖入口、字段、提交/保存类操作
- [ ] 验收结果含成功与异常场景
