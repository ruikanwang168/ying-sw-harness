# PRD 基础写作规则

## 文档信息与材料

- 按目标项目要求填写元信息。日期使用实际本地日期，负责人沿用用户指定信息；缺失负责人时按项目规则填写，不虚构业务审批人。
- 更新记录只记录真实新增或变化，不编造历史版本、上线时间和审批结论。表格可用“版本／日期／变更说明”，其他列有需要再加。
- 相关材料集中列出实际使用的需求、原型、UI 和旧 PRD；不生成空链接。正文只在有歧义或依赖时补来源定位，不为每个字段附源码证据。
- 用户已有公司模板时沿用它。模板中的方括号是写作提示，生成时替换为真实内容；无适用内容的节直接删除。

## 背景、目标与范围

新需求用一小段交代谁遇到什么问题、此次解决到哪里。迭代直接说明本次变化，补适用与排除范围；不为每个模块重写产品定位、愿景和价值。

目标可定性。只有材料提供或用户授权明确制定了量化目标时才写数值，并区分目标与实测结果。没有依据时，不填写效率提升百分比、响应秒数、容量上限或上线日程。

## 规则、来源与缺口

- 优先采用用户已确认的需求；原型、旧 PRD 或源码冲突时说明具体分歧，不能默默选一种。旧 PRD 仅在适用范围内作为存量依据。
- Mock 用户、演示金额、硬编码日期等用于理解展示，不自动成为业务取值和约束。临时调用地址仅用于理解数据流。
- 用户授权自行判断时，可在授权范围内补充合理设计，集中说明影响业务的重要决定；不可补造真实人员、数据来源、接口能力、历史事实或批准状态。
- 已有规则明确时完整写出。未知项会改变范围、权限、状态、计算或验收时，在对应位置标注“待确认：具体问题”，末尾集中列问题和影响；同一问题不重复建项。
- 未指定的非关键实现细节可留给研发；不要为了表格列齐全，逐个追问列宽、字段技术类型或图标。

## 一条规则一个定义位置

- 局部规则写在功能内；角色权限、统计口径等跨功能复用规则可集中成节并编号。
- 页面引用公共规则时写明确标题或编号，并写自己的例外；不用“同上”等无法定位的指代。
- 同一字段不在列表、表单、详情和附录中反复定义。列表补展示格式、排序等差异，表单定义输入约束，详情补只读展示差异。
- 表格用于需要逐项对照的字段、权限、状态或计算规则；简单动作使用短条目，不强制把所有内容表格化。

## 用户故事与验收

用户要求故事或已有故事需要关联时，沿用故事 ID 和角色、场景、目标。不另造一套同义编号。

验收要点表达“在什么条件下，操作后看到什么结果”，覆盖核心成功路径和会改变结果的重要异常。可在功能内集中列出，也可在文末汇总，选一个位置作为主定义，不两处重抄。无需展示 EARS 分类标签或为每个按钮独立编故事。

## 非功能与技术边界

只写有业务依据的性能、安全、兼容、数据保留等要求。通用规范已由项目统一约定且本期无变化时引用既有约定，不重新扩写一章。

需要研发提供的能力用业务语言描述，例如“保存时拒绝已被他人修改的旧数据，并保留当前输入”。锁实现、版本参数、HTTP 方法、索引和事务方案属于后续技术设计，除非用户明确要求，不在 PRD 中展开。
