# ProtoToPRD：原型转产品需求文档

## 定位与边界

从原型中还原本次需求，生成供产品、设计、研发和测试共同阅读的中文 `PRD.md`。默认采用“需求范围 → 功能清单 → 必要流程与公共规则 → 功能说明 → 验收要点”的组织方式，优先沿用用户提供的公司格式。

- 输入可以是原型代码、可运行原型、截图，以及需求材料、旧 PRD。只有文字且没有原型时，说明本次依据文字整理，不声称已核验界面。
- 评审或修改本技能文本，不触发下述 PRD 生成工作流。
- 本技能不实现业务代码，不默认设计正式 API、数据库、前端路由、完整测试用例或研发执行计划。外部系统依赖、数据来源和业务处理结果仍须说明。
- 用户明确要求更细的研发规格时，仅扩展被要求的部分；不能因此自动为所有页面增加完整工程章节。

## 核心输出原则

1. **覆盖完整，表达集中**：纳入范围的功能、字段、按钮、状态和业务异常不得因精简而遗漏；覆盖不等于每个控件都独立成章。
2. **同一规则完整定义一次**：跨功能共用规则集中说明，页面只引用并补差异；局部规则留在对应功能。验收要点写可观察结果，不重抄完整规则。
3. **按复杂度组织**：同一业务对象的新建/编辑共用字段表，单列默认值、只读、权限、校验和保存后的差异。简单确认弹窗放在触发操作下，复杂分支或独立业务任务才另设小节。
4. **仅输出适用内容**：没有筛选、分页、批量操作的功能，省略对应小节；不生成“无独立搜索／不适用”表格。不为凑模板增加能力。
5. **图表服务理解**：已有清晰原型时不重复画 ASCII。跨角色流转、复杂状态或难以用短文说清的分支，选择流程图或状态表；普通查询、保存、取消不要求配图。图后只补易误解的业务说明，不逐节点复述。
6. **业务语义优先**：描述展示内容、触发条件、权限、计算口径、处理结果和失败后的业务状态；不把 Mock 值、组件变量、临时接口当成正式需求。
7. **事实与设计分开**：识别材料冲突、原型残留或交互死路。用户已确认的目标优先，原型现状不能覆盖它；推测的设计意图只能作为建议。会改变范围、计算、状态或权限的缺口须明确处理，不能暗自补造。
8. **按影响补缺口**：未知信息只在影响实现或验收时列为待确认。未指定的列宽、图标、非关键字符长度不必逐项追问，也不能编造。不得套用固定响应时间、效率提升比例、导入上限等数值。

## 第一阶段：解析与范围盘点

### 1. 确定输入与本期边界

先遵守目标项目的访问规则和扫描边界，再读取用户指定材料。源码可直接读时先读；实际布局和交互须核验时使用环境可用的浏览器能力；截图输入结合视觉阅读。工具不可用时说明未核验部分，不假装完成浏览或运行。

根据已有上下文判断：

- **新需求**：说明要解决的问题、使用角色和本期功能范围。
- **版本迭代**：识别新增、修改、下线及受影响的旧行为，围绕本次变化写。用户要求更新原 PRD 时保留未变内容；要求独立版本文档时写本期变更及必要背景，不复制整个系统。

只有分支歧义会影响交付时才询问，并给出“新需求／版本迭代”或“更新原 PRD／独立版本文档”等明确选项。不要求用户重复选择已说明的模式。

### 2. 识别功能与业务规则

内部维护完整盘点：模块、页面及辅助界面、字段、按钮、入口与返回、角色权限、状态流转、计算口径、数据来源和重要异常。已有页面/故事 ID 可沿用；新建 ID 仅用于核对，无须默认出现在正文。

重点检查：

- 列表的筛选匹配、组合关系、默认条件、排序、展示字段及行操作。
- 表单的类型、必填、取值、默认、联动、只读及新建/编辑差异。
- 按钮的可用条件、业务动作、跳转/弹窗、成功结果和重要失败结果。
- 数量、金额、日期、百分比的单位、分母、范围、去重、精度及空值含义。
- 状态/角色变化对可见、可编辑、统计和后续操作的影响。
- 多端、外部服务、导入导出、历史数据等明确纳入本期的特殊能力。

原型没有实现的校验不等于业务不需要校验；也不能凭通用组件库自行新增功能。已有事实不足时，区分“待确认的业务规则”和“研发后续确定的实现方式”。

### 3. 展示简短盘点并确认

在对话中集中展示本期范围、按模块的功能清单、关键规则、材料冲突和影响决策的待确认项。不同时堆叠功能树、需求卡片、风险雷达和多份同义清单。

首次生成且尚未获得范围确认时，在此暂停等待确认。用户已确认同一范围、要求直接生成，或明确授权自行判断并继续时，按已有授权推进，不再次索取同一确认。授权设计不能替代真实业务数据；无法确定且影响核心行为的冲突，说明阻塞点，先完成不依赖它的部分并标为草稿。

## 第二阶段：组织与生成 PRD

### 4. 选择结构和内容粒度

优先用户指定模板；否则使用常规模板。AI 能力作为对应功能的补充，不自动另起一套 Agent 故事、协作时序、提示词、数据集与成本章节。

- 功能清单是面向评审的范围入口，按“模块／功能／说明”列出；迭代可增加变更类型，复杂权限可增加适用角色。
- 功能说明围绕业务模块及用户任务分组。复杂独立页面可设小节，共用表单与轻量弹窗按核心输出原则合并。
- 有真实原型图片或链接时放在功能附近，并说明其对应区域；无图片可用文字说明，不用通用布局冒充已核验的原型。
- 涉及多角色、多阶段、回退或修改分支时，提供必要流程或状态映射，覆盖实际存在的重要异常路径；不要求所有功能都进入一张主流程图。
- 用户故事仅在用户要求、公司模板采用，或已有故事需要追踪时展示，沿用已有 ID。业务价值通常可在功能说明中直接表达。
- 跨功能公共规则有复用价值时集中定义。字段优先使用业务中文名称，不默认附英文接口字段、列宽、图标和证据列。

### 5. 控制正文边界

默认正文包括更新记录、相关材料、需求范围、功能清单、适用的流程/公共规则、功能说明、关键验收要点及真实待确认事项。章节可合并或省略，没有内容不留空标题。

默认不展示：内部覆盖矩阵、流程节点对账、模板章节映射、生成过程说明、逐页面代码证据、完整技术契约、全量数据字典、完整测试用例。可追溯信息在内部保留；用户需要时再单独交付，不自动生成附件或把冗余搬到附录。

不得用“详见规范”“以下略”“后续同样处理”等省略应交付的业务规则。引用本文已定义的公共规则或同一表单是允许的，必须能定位，差异和例外写清楚。

### 6. 核对与交付

按自检清单逐项核对盘点与正文，允许多个页面映射至同一功能小节，但每个纳入范围的行为都要有落点。发现遗漏补业务内容，发现重复合并规则；不以字数、独立标题数或图表数判定通过。

- 输出到用户指定位置；未指定时写当前交付目录的 `PRD.md`。不默认覆盖无关文件或改原型代码。
- PRD 使用中文、标准 Markdown；需要流程图时使用 Mermaid。文档头部按目标项目规则维护日期、状态和负责人，未定业务规则影响交付时标为 `draft`。
- 交付消息只说明文件位置、范围和未解决的重要问题；不把内部检查过程写成正文证明材料，不声称完成未执行的测试或运行核验。
