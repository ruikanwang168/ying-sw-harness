# PRD 结构选择

先写本次目标和交付范围。需要多个读者快速分工时，用短功能清单交代模块、功能或变更、适用端与上线范围，随后沿功能清单展开说明。正文把界面、业务行为和验收结果放到读者会查找的位置。

## 按变更规模组织

- **新功能或大版本**按功能清单、主流程、详细功能组织。审批和跨系统场景用状态表列触发条件、角色、动作和流向。页面复杂时把原型和关键规则放在同一小节。字段规则较多时用字段表。
- **增量或日常优化**按上线批次、模块或改动项组织。每个改动说清影响范围、目标行为、例外与结果。受影响的沿用规则在对应项引用。小改动可用一段或一行，但需要独立验收的差异应可定位。
- **研发规格**沿用业务功能作为阅读顺序。针对受影响的操作补足字段约束、页面状态、系统处理、接口映射与验收。长接口、映射或数据规格可在对应功能下或附录展开，并从正文链接到具体位置。
- **公司格式**以用户提供的现行样例为准，按本次规模使用适用章节。来源材料中的版本变更、撤销标记、待确认和边界条件应按目标版本核实后表达。

有判定价值的内容随场景展开。后台系统侧重角色与数据范围、批量操作和筛选。审批系统侧重节点、分支、状态和异常。数据产品侧重指标口径、粒度、延迟和钻取。AI 功能侧重输入输出、失败反馈、人工兜底和验收。接口型能力侧重调用方、业务契约、权限、回调和异常结果。

规则写在最便于定位的位置。功能清单只摘要，详细条文统一引用；长表仅在需要横向比较时使用。篇幅缩减通过共用规则和省去无关背景实现，范围内的行为、例外与验收结果均须可定位。
