# 需求依据与功能覆盖

## 从材料建立清单

1. 确定本次交付的项目、版本和适用端。记录覆盖材料及访问情况。对跨版本资料标明各条需求实际归属的发布批次、已确认的变更、明确下线或取消项。版本口径不一致时保留各自来源并确认目标版本。
2. 从需求、清单、图表、原型、附件、已有代码和运行证据分别提取功能条目。需求明确但代码尚未实现的项目仍纳入覆盖。为界面逐个盘点页面、弹窗、抽屉、入口、控件、字段、表格列、查询条件和状态。为非界面能力盘点触发事件、任务与回调、系统集成、数据处理、输出和失败结果。合并重复资料时保留各自定位。
3. 对新增、变更和下线项顺着触发方与结果继续核对影响。按需检查 PC、H5、批量和其他入口，角色与数据范围，默认、空数据和异常状态，字段校验与联动，历史数据与权限，状态迁移、统计与导出、通知、自动任务及上下游读写。需求没有提到的关联能力先核实现状和受影响原因，再确定是否属于本次范围。证据不足时记录问题及影响。
4. 记录每项的业务对象、动作或规则、适用范围、来源位置、依据状态和处理结果。事实、合理推断、待确认与冲突分别记录。文档定位用路径及标题或表格行，原型用页面和状态，代码用相对路径和符号，运行证据用入口、角色、状态和记录位置。现状依据和目标规则分别标明。大版本可按模块记录，小需求可用短清单。

## 用实际成稿反查

| 对账结果 | 判定依据 |
| --- | --- |
| 已覆盖 | 实际成稿或随文附录可定位。对应入口、适用条件、处理与可观察结果写足。合并写法能定位各端、各角色和独立例外。 |
| 引用既有规则 | 共享或沿用规则有明确出处，已核对适用的版本、入口、角色或数据范围。正文指出哪些情形适用。 |
| 范围外 | 有明确依据表明该项与本次交付无关或已确认排除，并保留理由。 |
| 待确认或冲突 | 说明缺失材料、分歧或无法核验的事实，定位相关功能与影响。待确认项单独通过交付阶段规则判断是否阻断研发。 |
| 未覆盖 | 清单中存在范围内条目，成稿无法定位，或缺少影响实现与验收的规则。补齐后重新对账。 |

复核时逐项读实际条文。页面名、截图或「同原流程」只有在能找到生效规则和适用条件时才构成可复核说明。再反查成稿中新增的规则、权限、状态、接口和数据结果，确保能追到本次依据。重点核对同名动作的分支、手动与自动触发、失败后的数据与状态，以及变更两端之外的通知、统计或集成结果。

将影响评审和开发的缺口带进交付说明。已确认目标规则与实际运行验证分别记录。内部清单可直接服务复核，通常只需向读者呈现覆盖范围、可核实的依据和剩余缺口。
