# PRD 生成

生成供产品评审、研发和测试使用的 PRD。以本次交付的业务结果为主线，让读者从功能或变更项找到适用角色、入口、操作、业务规则、页面与数据结果，以及影响验收的边界。

**每个范围内功能都必须有可定位、可验收的说明。功能覆盖是交付门槛，正文篇幅由业务变化和读者的决策需要决定。**

## 确定范围和依据

列出材料、目标版本、交付范围、访问情况和关键缺失。至少需要一种表达目标需求的材料。有相关代码时，用它核实现状、影响和依赖。检索优先用 `rg --files` 和 `rg`。需要快速识别目标工程边界时，在技能目录运行：

```bash
python3 scripts/inventory_project.py <项目目录> [--output <盘点.json>]
```

- **新建或全量梳理**覆盖本次交付范围内的全部业务能力、页面行为、后台能力和集成。
- **版本增量或日常优化**先确认版本、发布批次、基线及新增、变更、下线事项，再追踪受影响的终端、角色、页面、状态、数据、接口和自动行为。受影响的沿用规则给出具体依据和引用。范围有实质歧义时，列出可选范围、依据和影响，请用户裁决。
- 区分目标需求与现状，保留材料定位。会改变范围、核心规则或业务结果的冲突须明确双方描述和影响，相关结论在用户裁决前列为待确认。页面、数据、接口和验证结果以可核实材料为依据。
- 遵守目标项目的资料访问边界。登录、写入数据、生产环境和敏感资料验证按现有授权范围执行。

## 建立功能覆盖清单

起草前读取[需求依据与功能覆盖](references/evidence-model.md)。从原始材料逐项建立内部清单，至少覆盖业务功能、操作与展示、角色和数据权限、不同终端和状态下的差异、系统自动行为、接口及跨系统联动。用原型和相关代码交叉核对入口、隐藏分支与间接影响。审批流、自动任务、外部回调、导入导出、消息通知、历史数据等按实际影响纳入。

范围内每个独立业务结果、页面行为或例外都要找到对应的正文、附录或明确引用。相同行为可以合写，并列明适用入口或场景。不同角色、终端、状态、规则或结果的差异分别对账。清单可保留在内部，用户要求追溯时随文交付。

## 按业务功能写正文

选择结构时读取[PRD 结构选择](references/prd-structure.md)。新功能或复杂改造通常先写目标与范围、功能清单和核心流程，再按模块、页面或场景说明。日常优化可直接按上线批次或改动项写清影响范围与验收结果。使用用户提供的公司格式时，保留其阅读顺序并为每项范围内行为找到位置。

- 涉及页面时，记录受影响的控件、字段、查询、展示和页面状态。业务差异写到可以验收。共享交互明确适用范围和规则引用。详见[页面说明要求](references/page-description-rules.md)。
- 涉及核心操作、自动行为或业务分支时，写清触发和前置条件、处理规则、可观察反馈、数据与状态变化、关联影响及失败后的结果。详见[业务操作研发契约](references/operation-contract.md)。
- 涉及接口、系统集成，或用户要求接口级研发规格时，按对应功能写清业务契约。需要完整参数、校验和调用映射时，可放在对应功能下或附录。技术架构、数据库物理设计和代码实现留给技术设计。详见[页面、控件与接口覆盖标准](references/page-interface-spec.md)。
- 难以判断功能拆分粒度，或需要判断增量影响写到哪里时，参考[功能粒度示例](references/examples.md)。
- 需要运行验证、页面链接或截图证据时，按授权环境执行并记录核验范围。详见[运行与截图规范](references/screenshot-runbook.md)。

## 交付前逐项对账

1. 从原始材料和影响范围复核清单，再逐条对照实际成稿。每项检查表达位置和覆盖结果。只写了功能名、只贴图、只留章节标题或只记在内部清单的条目仍需补齐。再从成稿反查依据、目标版本和范围。
2. 发现遗漏先补稿并复查关联项。材料缺失、规则冲突或访问受限时，明确受影响能力、已知事实、待确认问题和交付影响。只有有依据的范围外项才可关闭，未核实项单列。
3. 在文档中标明阶段和验证范围。范围或核心主流程尚未确定时标记 `需求草案`。范围与主流程已形成、仍有阻断研发或关键验收的问题时标记 `研发评审稿`。范围内功能逐项对账通过，核心行为、条件、权限、状态、数据结果和相关业务契约可据以开发验收时，才标记 `研发基线`。

在技能目录运行以下机械检查，处理适用的发现后交付：

```bash
python3 scripts/validate_prd.py <PRD.md>
```

脚本检查图片、占位、重复、模糊表述和待确认字样。对照实际问题核实未决项及其影响。功能完整性的判定依据是逐项对账的结果。交付摘要说明覆盖范围、仍待确认的事项及验证情况。
