# PRD Gen

## 目标与边界

产出一份可直接进入产品设计、技术设计、功能研发和测试验收的研发规格。研发应能逐页面、逐控件、逐接口判断实现内容、业务逻辑、数据与状态结果、异常边界及完成标准。技术架构、数据库物理设计和代码实现由研发另行设计。

分析过程、功能层级、章节、表格、列表和图表均由模型根据项目类型自主选择。不可省略的是页面、控件、接口和前后端结果的事实覆盖，不是某种清单、编号或排版形式。

不把当前代码自动视为目标需求；不虚构页面、字段、角色、权限、状态、接口、截图或运行结果；不修改业务代码、依赖或环境配置。

## 输入检查

开始时列出可用材料、分析范围、可访问状态和关键缺失。至少需要一种能够表达目标需求的材料；目录内存在相关代码时应分析相关部分。

优先用 `rg --files` 和 `rg` 检索。需要快速识别代码边界时运行：

```bash
python3 scripts/inventory_project.py <项目目录> [--output <盘点.json>]
```

不要读取 `.env`、密钥或无关目录中的凭据。多个候选项目、启动入口或范围无法可靠区分时，说明依据并请求用户决定。

## 不可跳过的决策闸门

- 将结论区分为明确事实、合理推断、待确认和冲突；内部保留可复核的材料定位。
- 需求、原型和代码对同一业务规则有实质冲突时，列出影响并等待用户裁决；不要自行指定来源优先级。
- 功能范围、核心角色或关键业务结果存在会改变交付物的歧义时，先输出候选范围供用户确认，再写完整 PRD。
- 需要登录、写入数据、使用生产环境或处理敏感数据时，先取得授权；无法安全验证时如实说明。

除上述情况外，自主选择阅读顺序、内部分析方法、功能分组、文档结构、图表、截图数量和措辞。不要为了套模板而生成不适用的章节或规则。

## 分析要点

根据材料与系统类型，覆盖真正影响交付和验收的内容。通常包括目标用户与场景、范围、业务流程、页面或能力、规则、字段、状态、角色与数据范围、异常处理、依赖和验收结果；没有证据或与该系统无关的项可省略，并在必要处标记待确认。

特别关注：

- 后台/运营系统：数据范围、角色、批量操作、筛选与异常。
- 审批/流程系统：节点、条件、状态转换、撤回与异常路径。
- 数据产品：指标口径、时间范围、粒度、延迟、筛选和钻取。
- AI 产品：输入输出边界、不确定性、人工兜底、评估与失败反馈。
- 平台/API 产品：接入流程、配额、回调、兼容性、幂等或安全边界。

对页面或交互原型，逐页面盘点按钮、链接、输入框、文本域、单选/多选、选择框、日期/时间、上传、查询条件、标签页、表格列、行操作、分页、弹窗/抽屉、键盘触发、只读展示项、汇总指标和全部页面状态。每项都要在最终文档中可定位；可集中说明，也可嵌入页面、场景或流程章节。通用交互可以引用统一规则，但不能遗漏。

业务权限使用角色、条件、允许操作、数据范围和无权反馈表达。已有或已确认接口的路径、方法、请求响应字段和业务错误可以进入接口规格；代码中的权限码、角色 ID 和内部实现条件只作为依据，不直接替代产品规则。

## 业务操作闭环

读取 [references/operation-contract.md](references/operation-contract.md)。以有独立业务条件、处理或结果的操作为基本单元，逐项写清：

- 用户、角色、入口、触发条件和操作前置条件；
- 页面初始状态、字段、按钮条件、校验、处理中状态和成功/失败反馈；
- 后端必须完成的业务校验、处理顺序、业务对象读写、关联影响和返回结果；
- 数据新增/修改/删除、状态转换、记录/通知/任务等副作用；
- 无权、无数据、重复、并发、依赖失败、部分成功和可重试规则中适用的部分；
- 可由研发和测试判断完成与否的验收标准。

页面上的每个按钮、输入框、选择框、查询项和展示项都必须有可定位的规格说明。普通导航、分页、标准关闭等可引用通用规则；保存、提交、审核、撤回、删除、导入、导出、批量处理、状态切换、自动任务等必须形成独立闭环。材料没有定义的页面或后端行为标记待确认，不要自行发明。

## 页面与接口规格

读取 [references/page-interface-spec.md](references/page-interface-spec.md)。无论采用何种结构，都必须覆盖：

- 每个页面/弹窗/抽屉的入口、角色、状态、数据来源和定位；
- 每个控件的类型、默认值、取值/展示、必填与编辑条件、校验、联动、权限、触发结果和异常表现；
- 每个接口的用途、调用方、触发操作、方法与路径、请求/响应、前置校验、分步处理、数据读写、状态变化、副作用、幂等/并发、异常和权限；
- 每个页面动作与接口、页面结果、数据/状态结果之间的关系；纯前端行为明确说明无接口，接口反向说明调用页面、系统任务或外部调用方。

这些内容可以按模块、用户任务、页面、业务流程、领域对象或接口组织；可以使用段落、列表、表格、图示或组合形式。不要强制页面编号、控件编号、接口编号、固定表头、固定章节顺序或统一层级。

当接口已经存在，从代码追踪路由/控制器、服务、模型和调用位置，描述实际逻辑并区分目标需求；当接口尚未存在但需求已确认，可定义研发所需的业务接口契约。材料不足以确定路径、字段或处理规则时写待确认，不得猜测。表名、SQL、框架类、缓存、队列和内部算法仍由技术设计决定，除非它们本身就是已确认的外部契约或业务约束。

## 交付阶段

在文档中明确标记以下一种状态：

- `需求草案`：范围或关键规则尚未确认，不可据此开发。
- `研发评审稿`：主要闭环已形成，可评估技术方案、成本和风险，但仍有阻断研发的问题。
- `研发基线`：页面、控件、接口及其关系已完成逐项对账，核心操作闭环、范围和规则已确认，可进入开发；剩余待确认项不得影响页面交互、接口契约、主流程、数据结构、核心状态、权限或业务结果。

只根据材料完整度标记状态，不因用户期望或文档篇幅擅自标记为研发基线。

## 运行与截图

只有在页面截图或运行验证确有助于交付时，读取 [references/screenshot-runbook.md](references/screenshot-runbook.md)。需要时使用真实 HTTP(S) 页面、实际终端视口和可复核的状态；静态原型、源码路径或已有图片不能冒充运行验证。

## 生成与检查

直接根据材料与目标读者生成结构，不从预设模板起稿。最终 PRD 应明确交付阶段、范围、逐项覆盖结论、冲突、待确认及验证状态。页面、接口、链接、截图或源码定位只有在材料确实提供或需求已确认时才写成事实。

交付前运行：

```bash
python3 scripts/validate_prd.py <PRD.md>
```

该脚本只检查占位符、失效图片、重复内容、模糊措辞和未决项等机械风险，不检查固定结构，也不能证明页面、控件或接口已经覆盖完整。交付前必须由模型对照材料逐项复核覆盖情况，并报告遗漏、无法确认和验证状态。
