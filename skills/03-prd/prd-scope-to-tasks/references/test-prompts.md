# 行为回归场景

维护技能时核对以下场景，验证实际清单内容与材料一致，不只检查列名。

## 1. 已有故事与现有页面修改

材料：已有故事“准确答复退款进度”；现有列表和进度查询已实现，本次只增加异常原因摘要。

期望：保留故事；前端页面修改、后端查询修改、测试分别拆行；说明现状与变化，不标成全新退款模块；人员和预计工时为空。

## 2. 多页面、多接口

材料：一个故事包含列表、详情两个页面，查询、保存两个接口。

期望：同一故事下至少分开两个页面任务、两个接口任务，并根据验证范围拆测试；不用“前后端开发”一行概括，不要求路由、请求方式或路径。

## 3. 共享工作与跨故事复用

材料：两个故事都修改同一列表或共用同一接口。

期望：共用工作由主要故事承接，详细说明关联全部相关功能，其他任务依赖它；不重复生成估工行，不为每个故事硬凑三角色。

## 4. 本次全量不是全系统全量

材料：现有代码有十个模块，本次仅改退款模块两项能力，审批明确排除。

期望：功能清单只含本次两项，菜单沿用实际结构；不纳入其他模块，不要求补三级菜单；代码已实现部分不能误标新增。

## 5. 材料冲突与代码缺失

材料：边界明确不做导出，原型却有导出；PRD 未解释；或无法访问现有代码。

期望：已确认部分先整理，额外导出作为冲突列出；无法核实的新增/修改放在待确认部分，不因未查到代码而标新增，不宣称完成全部核验。

## 6. 缺少故事、后台能力和删除

材料：有业务目标但没有故事；本次移除旧回调处理，不涉及页面。

期望：按业务目标补故事并标明来源，产生后端和测试删除任务，不凭空加前端；后台功能菜单可为“无”，说明原能力与移除影响。

## 7. 单份交付与已有估时

请求只要任务或只要功能时，仅输出所需清单，不强制附完整多层需求。用户明确提供人员和估时并要求录入时保留这些值；使用 `--only tasks` / `--only functions` 和 `--allow-filled-estimates` 对应校验，不默认猜测。

## 脚本回归

运行 `python3 scripts/test_validate_output.py`，验证有效交付、空文档、缺失清单、非法角色/变更类型、默认空值、功能引用与 CLI 返回值。它不能代替对上述行为场景的语义评审。
