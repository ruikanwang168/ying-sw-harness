# 清单填写与范围核对规则

生成任一清单前读取；这里负责拆分粒度、现状比较和两份清单的关联，不要求额外产出分析文档。

## 材料与代码怎样共同使用

- 先识别用户确认的本次范围及排除项，再核对原型和 PRD；新旧版本材料不能不加区分地混用。
- 代码核查围绕相关菜单、页面、前端调用、后端业务处理和现有测试，建立“已有能力 → 本次目标”的差异；按目标项目要求使用结构检索工具或源码检索，不能把搜索未命中当成不存在。
- 原型和 PRD 不一致，或代码已满足材料中的部分能力时，说明具体差异。边界材料无法消解且会影响交付的冲突列为待确认，不自行选择较大的范围。
- 输入未提供、链接打不开、代码不完整等情况需说明实际核查范围。可以交付带缺口说明的草稿，但不能宣称已确认全部功能或变更类型。
- 变更类型证据不足的条目放在清单外的待确认部分，注明“变更类型待确认”，不要伪造新增/修改结论；其余可确定条目继续整理。

## 用户故事与拆分粒度

- 已有故事优先沿用名称、编号和业务目标。编号缺失时补充 `US-001` 等编号；只包含宽泛章节时按独立业务目标组织，不机械把章节当故事。
- 材料没有故事时，从角色、场景和业务结果补充，说明其来源于材料推导；故事描述业务目标，不把页面、按钮、技术步骤当成业务价值。
- **前端**：每个需要变更的页面一条；可独立交付、评估的弹窗或抽屉可另拆。同页多个字段或按钮通常归为一条，不按控件拆任务，也不把多个独立页面合成一条。
- **后端**：每个需要新增、修改或删除的接口能力一条，以业务名称区分，不写请求方式或路径；不把多个独立接口合成“后端开发”。确有独立异步处理等非接口工作时，按业务处理能力补条目，角色仍为后端。
- **测试**：按本次故事下可独立评估的页面验证、接口验证、业务流程或专项回归拆分。每条写清正常、异常及受影响存量行为的验证范围，不只写“测试”。不机械复制每条开发任务，避免同一验证范围重复估工。
- 一条任务只对应一个人员角色。不强行为每个故事凑齐三种角色：仅后端变化可以没有前端任务，但仍需判断测试范围。
- 共用页面或接口只拆一次，由主要故事承接；其他故事写明依赖该任务。一个页面/接口涉及多个故事时，在任务详细说明中补充覆盖的故事，不重复形成估工行。
- 已实现且本次不需修改的页面、接口，不生成无实际工作量的开发任务；本次影响到的存量行为可进入测试任务验收范围。

## 任务行怎样写到能估工

任务编号用 `T-001` 等形式写在任务描述中，功能编号用 `F-001` 等形式写在功能描述中，不另加列。故事已有业务编号时保留。

每条任务详细说明写清：

- **关联功能**：对应一个或多个功能编号。只交付任务清单时，也保持可在文内识别的功能编号与能力名称，但不强制附另一份清单。
- **本次工作内容**：具体要交付什么；修改任务写“现有……；本次改为/增加/移除……”，说明数据展示、业务行为或状态规则的变化，不重复整份 PRD。
- **验收要点**：团队能据此判断完成的可观察结果，覆盖相关规则、权限、异常与受影响旧行为；有材料依据才写明确数值，不自定超时、分页量或权限策略。
- **依赖项**：引用任务编号、所需业务确认或外部条件。无依赖写“无”。测试任务关联所需开发任务；不要把实现方案当依赖条件。

测试行的变更类型表示被验证功能的变化，不表示“新增测试用例”。同一验证任务覆盖新增和修改时，按变更类型拆行并区分验证范围。

人员与预计工时默认必须是真正的空单元格。用户后续提供人员或工时并要求录入时可填写；Markdown 校验增加 `--allow-filled-estimates`，不擅自覆盖已确认值。

## 功能清单怎样写到能对齐范围

- “全量”只包括本次版本确定的全部功能变化，不包含全系统存量盘点。
- 一行一个可独立确认的产品能力变化，不以接口数量替代功能数量；一个功能可以有多个页面与接口任务。
- 模块和菜单层级按原型、PRD 或代码确认。不足三级的层级写“无”；非菜单后台能力同样可列入，菜单写“无”；归属缺少依据时写“待确认”，并在清单外说明。
- **功能描述**：功能编号和一句话能力名称。
- **功能说明**：写“现状：……；本次变化：……”，必要时补角色、主要规则及影响。新增写原先缺少什么能力；修改写现有行为与目标行为差异；删除写移除范围和使用影响。
- 一项能力同时含新增字段与旧规则调整，但整体是已有能力的改造时，标为“修改”并说明具体变化；只有独立新能力才另列“新增”。
- 仅作为前置条件使用的原有功能不单独列为本次功能，可在说明或任务依赖中引用。

## 交付前双向核对

1. 边界、原型和 PRD 中本次确定要交付的每项功能都已覆盖；代码中无关存量功能未被带入。
2. 功能编号与任务中的关联一致，每个功能至少有一个相应任务；每个任务都能追溯到本次功能和故事。
3. 现状与本次变化有依据。已实现部分未被误标为新增，共用工作未重复估工。
4. 任务足以独立估工，没有“前后端开发”“整模块开发”等混合大项，也没有按控件过度细分。
5. 人员、预计工时留空，列名、角色和变更类型符合模板；没有用路由、接口协议或底层设计替代工作说明。
6. 两份清单涉及的用户故事、功能、变更类型和依赖一致。冲突、未知项及未核实范围单列，不混入已确认结论。
