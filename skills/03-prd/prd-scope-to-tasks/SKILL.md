# 版本功能范围与任务拆分

## 交付目标

默认生成两份清单；用户明确只要其中一份时，只交付指定清单：

1. **任务拆分清单**：按用户故事分组，供前端、后端、测试分别评估工时。
2. **本次版本全量功能清单**：“全量”仅指本次版本的全部功能，明确新增、修改、删除及具体变化。

用户故事作为任务组织依据，优先沿用已有材料；不再默认生成独立用户故事文档、功能需求文档或多层研发规格。

## 输入与范围

输入包括本次版本的需求边界（可能已有用户故事）、原型、PRD，以及现有全量前后端代码。先确认材料对应的版本与代码基线；已有信息直接采用，不重复索取。

- 需求边界约束本次做什么，原型说明页面交互，PRD 说明业务规则，代码用于核实已有能力与改动范围。
- 全量代码是分析基线，不是全系统功能盘点授权。遵守目标项目扫描规则，围绕本次范围查阅相关代码。
- 材料缺失或互相冲突时，先完成可确定部分；把影响范围、变更类型、任务粒度或验收的缺口列为待确认，不猜测已确认结论。
- 不因原型出现额外页面、代码存在其他模块，就自动扩充本次版本范围。

## 执行流程

1. **核对材料与现状**：确认版本边界，交叉检查原型、PRD 和相关前后端代码，区分现有行为与目标行为。缺失代码证据不等于功能不存在。
2. **建立故事与功能对应关系**：沿用已有故事的编号和业务目标；缺失时按独立业务目标补充，标明“依据材料补充”。不按按钮、字段或菜单拆故事，不重写已确认故事的业务含义。
3. **盘点本次全部功能**：按模块、菜单和独立能力组织，明确每项现状、本次变化及变更类型。填写规则见 [references/list-rules.md](references/list-rules.md)。
4. **按故事拆任务**：前端按页面、后端按接口能力、测试按可独立评估的验证范围拆条；一条任务对应一个人员角色。每条说明本次工作内容、验收要点和依赖项。
5. **交叉核对并交付**：确认本次功能都有相应任务、任务都有范围依据，共用工作不重复估工；输出任务清单在前、功能清单在后。材料缺口和冲突在清单外单列。

## 两份清单的约束

### 任务拆分清单

固定七列，顺序不变：**用户故事、任务描述、任务详细说明、变更类型、人员角色、人员、预计工时**。

- 同一故事下可以有多条任务，每行写明故事编号与名称，便于筛选和导出。
- 人员角色仅为 **前端、后端、测试**；人员和预计工时默认留空，交由团队填写，不写“待分配”、0 或猜测值。
- 变更类型为 **新增、修改、删除**，依据所处理功能的变化填写；测试任务沿用被验证的变更类型。
- 任务详细说明包含 **本次工作内容、验收要点、依赖项**，并关联功能编号；修改任务须写清已有行为和本次改动。
- 不要求页面路由、接口请求方式与路径、代码符号、表结构、协议或实现方案。任务名称可用业务页面或接口能力名称区分工作。

生成任务清单前读取 [assets/task-list-template.md](assets/task-list-template.md) 和 [references/list-rules.md](references/list-rules.md)。

### 本次版本全量功能清单

固定七列，顺序不变：**模块、一级菜单、二级菜单、三级菜单、功能描述、功能说明、变更类型**。

- 功能描述用“功能编号 + 能力名称”，功能说明写具体能力、现状和本次变化，关联任务使用相同功能编号。
- 变更类型为 **新增、修改、删除**；必须说清是否修改现有功能，不能只写“优化”。
- 菜单层级依据材料或现有项目，不强行补足三级；确实没有菜单的后台能力可写“无”，无法确定的菜单归属写“待确认”。
- 未涉及本次变更的存量功能仅用于说明上下文，不因代码中存在就单独列入清单。

生成功能清单前读取 [assets/function-list-template.md](assets/function-list-template.md) 和 [references/list-rules.md](references/list-rules.md)。

## 条件加载与校验

- 遇到故事拆分、共享任务、代码与材料冲突、变更判定等问题时，读取 [references/list-rules.md](references/list-rules.md)。
- 需要完整填写示例时，读取 [references/example.md](references/example.md)。示例业务规则不作为其他项目的需求。
- 维护或验证技能行为时，读取 [references/test-prompts.md](references/test-prompts.md)。
- 默认按两个模板输出 Markdown 表格；用户指定 Excel 等格式时保留相同列和含义，并使用环境中适合该格式的工具。
- 保存为一份包含两清单的 Markdown 时，运行 `python3 scripts/validate_output.py <清单.md>`；只交付一份时增加 `--only tasks` 或 `--only functions`。
- 脚本仅检查表头、关键字段、枚举、默认空值和功能引用等机械规则，不能证明材料覆盖、变更判断或估工粒度正确；还须对照输入人工或由智能体复核。
